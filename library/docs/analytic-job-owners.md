# Analytic job owners

The owner of each analytic job, and the production chain that runs them. [Docs index](README.md)

One owner per analytic job (R-224). Every other implementation of the job is retired or a thin wrapper, and its header names the owner. A framework may include kernel L0 to L6 plus the L7 headers above (Framework, FrameworkSingleton, Rule, Constraint, Preference), never kernel L8 (`analysis/`), and the kernel depends on no framework (Law 11). A wrapper that joins an L8 analysis with a framework adapter therefore cannot live in either one: it lives in the `chain/` target above both (P22 B3). Where a framework needs an L8 owner and the chain does not apply, the caller injects it as a callback (the `StandardFormBoundaryDetector` pattern).

## The production chain

`analysis_chain_run` (`chain/analysis_chain.h`) is the one production chain from neutral notes (`semantics/analysis_note.h`, made from an import by the caller) to every analysis the libraries own. It runs the stages in the order of the dependency spec: segments, local key regions, weighted chords per region, Roman numerals, outer voices, cadences (with boundary cadences), phrase form (phrases, ideas, themes, expansions) and motive families, meter, texture, voice leading, melody, schemas and sequences. Each stage calls the owner of its job ([the owner table](analytic-job-owners.md#analytic-job-owners)) through an input builder in `chain/chain_inputs.h` (one `chain_inputs_<stage>.c` file per stage) and the run walks `analysis_chain_stages`, one table row per stage, which turns the notes and the earlier stages' results into the plain input the framework reads; no builder chooses a default. A stage subset (`AnalysisChainConfig.stages`) runs only the stages it names and the ones they need. The key regions depend on the phrases and the phrases on the keys, so the run goes through them twice (the first pass's chords are evidence and its phrase ends boundaries for the second); there is no further iteration. `AnalysisChain` owns every result and gives it back through accessors that return the frameworks' own result structs. No test glue runs analysis. The library's own tests run it through the chain: `chain/tests/weighted_pipeline.h` (segments and outer lines), `tests/accuracy/chorale_chain.c` (the accuracy harness) and `tests/integration/framework_v1_chain.h` (the reference pieces) call `analysis_chain_run`, and the integration tests that give a stage an annotation's answer (a home key, hand cadences, a written soprano) build its input with the chain's builders. What stays in the tests is expected-value parsing and comparison. Detail in `chain/README.md` and `docs/testing/`.
