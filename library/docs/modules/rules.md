# rules

Layer L7 (`music-rules`). Path `src/rules/`, tests `tests/rules/`. Sibling of `theory`, and the one L7/L8 sibling pair that is not mutually restricted. `Rule`, `Constraint`, and `Preference` each hold a direct, unowned `Framework` reference (the same reference-only pattern `Context` uses for its own parent field).

## Provides

`Rule`, `Constraint`, `Preference`, `RuleEvaluation`.

## Notes

- `Constraint`'s type is a tagged type, not a boolean. `ConstraintType` has five variants (`_HARD`, `_SOFT`, `_WEIGHTED`, `_CONDITIONAL`, `_CONTEXTUAL`, TDD §96), not a single `is_hard` flag. Only `CONSTRAINT_TYPE_WEIGHTED` uses the weight numerator/denominator fields; every other type ignores them. `constraint_evaluate` dispatches to an evaluation callback (`ConstraintEvaluateFn`) that a framework registers on the Constraint with `constraint_set_evaluate_fn`. A `Constraint` holds only that pointer: the framework owns the callback and any data behind it, and nothing owned is embedded in `Constraint`. A Constraint with no callback returns `CONSTRAINT_EVAL_NOT_IMPLEMENTED`. standard-harmony and standard-counterpoint register callbacks for every rule in their rule tables (a candidate `Value` carries a `standard-<framework>/<table prefix>` type tag and the rule's subject struct, borrowed for the call); no other framework registers one. Wiring evaluation into a generation pipeline is `generation` (L8) work.
- `constraint_evaluate` takes an optional `Context` (`context/context.h`) reference, `CONDITIONAL`/`CONTEXTUAL` constraints need ambient context to decide whether their condition applies. `constraint_evaluate` itself returns `NOT_APPLICABLE` for a `CONTEXTUAL` constraint called with no context; the condition `Value` is opaque, so any other condition is the callback's to decide. `ConstraintEvalResult` also gained `CONSTRAINT_EVAL_NOT_APPLICABLE`, reserved for a `CONDITIONAL`/`CONTEXTUAL` constraint whose condition does not hold -- kept distinct from `CONSTRAINT_EVAL_FAIL` so a caller aggregating scores downstream never conflates "did not apply" with "failed." `CONSTRAINT_TYPE_WEIGHTED` deliberately stays on the same PASS/FAIL/NOT_APPLICABLE contract as every other variant (weight is read separately via the existing accessors) -- no variant gets its own return shape.
- `Preference` cannot reject a candidate. `preference_rank` is structurally distinct from `constraint_evaluate`. Its result type has no pass/fail/invalid variant, only "computed" or "not implemented." No code path in `preference.h` lets a `Preference` invalidate a candidate the way a `Constraint` can. `preference_rank` dispatches to a scoring callback (`PreferenceScoreFn`) that a framework registers on the `Preference` with `preference_set_score_fn`, mirroring `Constraint`'s evaluation callback: the `Preference` holds only the pointer, the framework owns it and the data behind it, and a `Preference` with no callback returns `PREFERENCE_RANK_NOT_IMPLEMENTED`. A score is an exact-rational `PreferenceScore` in [0, 1] (no floating point anywhere in scoring); a score with denominator 0 means the callback could not score the candidate. `preference_rank` takes an optional `Context`, passed to the callback. standard-harmony and standard-counterpoint build a `Preference` for each soft rule in their rule tables (accessors like `harmony_cadence_preference`), scoring a candidate 1/1 when the rule holds and 0/1 when it does not.
- Ranking orders candidates and never removes one. `preference_rank_candidates` (`rules/preference_ranking.h`) scores a candidate set against a weighted list of `Preference`s and writes the input indices best-first, stably, as a permutation: a candidate a `Preference` cannot score counts as the worst score, and on any error the input order is returned unchanged. A candidate's total is the weighted sum of its scores over the sum of the weights, computed by `rules/preference_weight.h` with reduced fractions and explicit `ERR_ZERO_DENOMINATOR`/`ERR_OVERFLOW` results, never silent wraparound. Hard rejection belongs to `Constraint` only.
- `RuleEvaluation` is the per-Rule evaluation outcome a `CandidateEvaluator` (`generation/candidate_evaluator.h`, L8) builds while judging a Candidate, and the shape that `CandidateEvaluation`'s own evaluations[]/violations[] would be assembled from -- confirmed with the project owner after this type was originally flagged as needing a decision (Registry-First Dependency Rule, Dependency Spec §6): no distinct Registry row exists for it, so this is a considered fit against `Rule`/`Constraint`/`Preference` and `CandidateEvaluator`'s consumption pattern, not a literal TDD field list. It holds a required `rule_id` reference (by id only, never embedded), a tagged `RuleEvalOutcome` (`_SATISFIED`/`_VIOLATED`/`_NOT_APPLICABLE`/`_NOT_IMPLEMENTED` -- `_NOT_APPLICABLE` mirrors `constraint_evaluate`'s own `CONSTRAINT_EVAL_NOT_APPLICABLE`), an optional owned `finding` (`Interpretation`, kept explainable per TDD §159), and an optional weight fraction (denominator 0 means "no weight recorded"). It has no identity of its own -- no `id` field, no `*_identity_equals` -- the same treatment `CandidateEvaluation` gets. This type only defines the shape and its own construction invariants; populating a real one from `constraint_evaluate`/`preference_rank` output against an actual candidate is `CandidateEvaluator`'s job (L8), the same L7/L8 split those two stubs already follow.
- **`RulePair` (`rules/rule_pair.h`).** Every framework backs a rule with one `Rule` and one `Constraint` that reference the framework. `rule_pair_build(framework, prefix, name, &pair)` builds both with the ids `"<prefix>-rule-<name>"` and `"<prefix>-constraint-<name>"` and a hard constraint. `rule_pair_build_typed` takes the `ConstraintType` for frameworks whose rules are hard or soft and refuses `WEIGHTED` (no weight is supplied). Each framework's `rule_pair.h` keeps its own typedef (`typedef RulePair <Framework>RulePair;`) and its `<framework>_build_rule_pair` as a static inline call with its own framework and prefix, so no rule or constraint id changed. standard-counterpoint and standard-harmony keep their own builders because they also register an evaluation callback and build a `Preference`.
