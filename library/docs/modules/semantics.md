# semantics

Layer L6 (`music-semantics`). Path `src/semantics/`, tests `tests/semantics/`. One of four L6 siblings; see `docs/modules/l6-notes.md` for rules shared across all four.

## Provides

`Interval`, `Sonority`, `SonorityBuilder`, `RhythmicPattern`, `Scale`, `Contour`.

Vocabulary enums (plain names, no `EntityID`, no framework claim; see `docs/ARCHITECTURE.md` for the admission rule): `VoicePart`, `MotionType`, `CounterpointSpecies`, `BeatStrength`, `NonChordTone`, `ImitationAnswer`, `FugueRole`, `OstinatoType`, `ImitativeRole`, `SchemaFunction`, `ScaleDirection`, `SequenceKind`, `HarmonicFunction`, `CadenceType`, `SeventhResolution`, `PhraseModelLabel`, `SixFourType`, `AppliedChordKind`, `ModulationKind`, `KeyChangeExtent`, `FormLevel`, `MotiveKind`, `PhraseRole`, `PhraseBeginning`, `PhraseEnding`, `IdeaLabel`, `SubphraseRole`, `ContinuationTrait`, `PhraseLevelForm`, `PhraseLengthChange`, `ExpansionPlacement`, `InternalExpansionTechnique`, `AlternativePathKind`, `ExternalExpansionKind`, `ExpectedLengthBasis`.

## Notes

- `Interval` and `Sonority` do not depend on `PitchClass`. `PitchClass`, `PitchRealization`, and `TuningSystem` now exist (`pitch`, L2 -- see `docs/modules/pitch.md`), but neither of those two types consumes them: `Interval` computes nothing itself, since `PitchIdentity` is an opaque token with no numeric semantics; each of `Interval`'s three dimensions (directed, undirected, chromatic distance) is supplied by the caller as an independently-optional field, never defaulted to zero when unknown. Diatonic distance (the fourth TDD §67 dimension) is not represented at all; wiring it up would need `PitchClass`, which neither type has done. `Scale`, below, is the first type in this module to consume `pitch/pitch_class.h` and `pitch/tuning_system.h`.
- `Sonority` is not a `Chord`. `sonority.h` carries no chord-identification logic (root, quality, inversion); that is `Chord` (`interpretation`, L6, built on top of `Interpretation`).
- `RhythmicPattern` has no pitch fields. `rhythmic_pattern.h` takes no dependency on pitch headers; a rhythmic query never needs pitch information.
- `Scale` is a Value (no `EntityID` of its own, same as `Sonority`): an ordered collection of `PitchClass` (owned, `pitch_class_count > 0`) under a `TuningSystem`, referenced by `EntityID` rather than embedded -- the same reference-only pattern `Sonority`'s `voice_ids` already uses. `Scale` has no `FrameworkReference`: an ordered `PitchClass` collection under a `TuningSystem` does not require an interpretive claim to exist. Contrast `ScaleDegree` (`interpretation/scale_degree.h`), which references a `Scale` and does carry one.
- `Contour` is a Value: a relative pitch-change sequence (`ContourDirection`: up/down/same) over a `PitchIdentity` sequence. Directions are caller-supplied, not computed -- the same principle `Interval` already establishes, since `PitchIdentity` carries no numeric semantics this module could derive a direction from. `Contour` has no `FrameworkReference`: an observed pitch-direction sequence does not require an interpretive claim to exist.
- `SonorityBuilder` (`semantics/sonority_builder.h`) derives `Sonority` objects from raw `NoteEvent`s, closing the gap chord identification (`analysis/chord_identification.h`) previously left on the caller: nothing in this codebase grouped sequential/arpeggiated notes into a `Sonority` before this. Each `NoteEvent`'s onset-to-release activity interval `[onset, onset + duration)` -- left-closed/right-open, the same boundary treatment `TIME_SPAN_BOUNDARY_LEFT_CLOSED` already uses -- is queryable via `sonority_builder_note_active_at` (System Registry Problem A's onset-to-release tracking). The grid-sampling step itself groups notes by ATTACK rather than by that full active span: each beat's `Sonority` is formed from every note whose onset falls within that beat's half-open window, on a FIXED one-sample-per-beat grid hardcoded to a quarter note. Grouping by onset rather than by full sustained activity is a deliberate, empirically-driven choice (validated against the fixture below): a note's duration commonly exceeds one beat in this repertoire (e.g. a held bass tone under faster-moving upper voices), and carrying it forward by sustain into every later beat it still rings through would contaminate each of those beats' `Sonority` with a stale tone instead of that beat's own attack content. This is a stated v1 default (System Registry Problem A: sampling at a fixed metric grid), not a general/adaptive harmonic-rhythm detector (Problem B) -- it does not infer chord-change points, does not vary its grid by texture or tempo, and the beat unit is not a parameter, the same fixed-constant-not-`config`-driven treatment `PhraseBoundaryDetection`'s `max_length_without_cadence` and `SentenceDetection`'s min-2-events continuation floor already use in `docs/modules/analysis.md`. Non-chord-tone tolerance and multi-voice/dense-texture handling (Problem B) are explicitly deferred: every note onsetting within a beat is included as-is, with no best-fit/passing-tone filtering -- `tests/analysis/test_bach_prelude_arpeggiated_chords.c` accounts for this by treating a measure as matching its expected chord when AT LEAST ONE of its four beat-grid `Sonority`s resolves to it, rather than requiring every beat's (possibly non-chord-tone-contaminated) sample to agree. Built and validated against solo/monophonic-texture writing only (`tests/fixtures/arpeggiation-investigation/Bach_Prelude_C_Major.mid`). A beat with no note onsetting in it produces no `Sonority` (`Sonority` requires `event_id_count > 0`) -- silence between attacks is a legitimate gap, not an error.
- `VoicePart` is a plain enum value (soprano, alto, tenor, bass, ordered highest to lowest) naming a role in a four-part texture. It carries no `EntityID`, range, clef, or framework claim, and it is not `Voice` (`containers/voice.h`), which identifies a single line and may be written as any part or none. Ranges, staves, and stems for each part are conventions of `frameworks/standard-voicing`.
- `MotionType` is a plain enum value naming how two parts move from one pair of simultaneous notes to the next: contrary, similar, parallel, oblique, or static (neither part moves). The categories are exclusive, and parallel is the refined case of similar (same direction and same distance), so `motion_type_is_same_direction` is true for both. It carries no `EntityID`, pitches, or framework claim. Deciding which type a pair of moves is takes pitch arithmetic, which belongs to a framework (`frameworks/standard-counterpoint`). It is not `VoiceLeadingMotion` (`analysis/voice_leading_analysis.h`), a caller-supplied observation of the four classic types with no static case.
- `CounterpointSpecies` is a plain enum value naming one of the five species of strict counterpoint (first through fifth, ordered simplest to most elaborate), with a helper for the counterpoint notes against each cantus firmus note (1, 2, 4, 2, and 0 for the fifth, which mixes ratios). It carries no `EntityID`, rules, or framework claim. What each species requires of a line is a convention of `frameworks/standard-counterpoint`.
- `BeatStrength` is a plain enum value naming the metric weight of a position in a bar: strong, medium, or weak, ordered from strongest to weakest so a smaller value is a stronger position. It carries no `EntityID`, time signature, or framework claim, and it is not the beat grid of a time signature (`time/time_signature.h`). Which positions of a bar have which strength is a convention of a framework (`frameworks/standard-counterpoint`): in two notes against one, the first note of each bar is strong and the second weak; in four notes against one, the four notes are strong, weak, medium, weak.
- **Adaptive sonority segmentation** (`semantics/sonority_segmentation.h`): a second, meter-aware way to cut notes into `Sonority` segments, `sonority_builder_build_adaptive`, next to the fixed-grid `SonorityBuilder`. The fixed-grid builder is unchanged (Analyzer, GUI and the existing tests use it, and callers move over later); this one does not group by attack on a quarter-note grid, ignore meter, or drop a note held into a later beat.
  - **Membership.** A segment holds every note SOUNDING in it, those attacked in the segment and those held over from earlier. `AdaptiveSonority` is the `Sonority` (its `time_window` is the segment's `[start, end)`, left-closed; event ids are clones of the notes' ids, in input order; no voice restriction; domain SOUNDING) plus `held[i]`, parallel to the event ids: true if the note was sounding before the segment began. `Sonority` itself is unchanged, since attacked-versus-held is segmentation metadata and not part of a selection's identity. Weighting by duration or metric position is not done here (that is the chord-identification work). The bass of a segment is its lowest sounding pitch.
  - **Pitch.** Pitch comes from each note's `PitchSpelling` as a semitone number (`12 * (octave + 1)` plus the letter's semitone plus the accidental, so C4 is 60); the pitch class is that mod 12. A note with no spelling is `AD_SEGMENTATION_ERR_NO_PITCH`, not skipped. The MIDI importer always sets one.
  - **Injected beat grid.** The beat grid is a `BeatGridProvider` the caller passes: a function that returns the beat starts of one measure of a `MeterMap`. The kernel cannot include a framework, so what a beat is arrives by injection, the same pattern the cadence ranking uses. `frameworks/standard-meter` supplies the standard provider (`standard_meter_segmentation_beat_grid`): 6/8 gives two dotted-quarter beats, 3/4 three quarter-note beats, 12/8 four dotted-quarter beats, and 5/8 five eighth-note pulses. A short measure is laid out from its own start and its last beat is cut at the barline; a pickup measure uses its offset from where a full measure would have started, so its beats fall where the full measure's would.
  - **The three steps**, in order, each its own internal function with its own tests: (1) the grid cut: one segment per beat of every measure up to the end of the last sounding note; (2) the bass split: a beat splits at the attack of a new lowest note, unless the new bass lasts less than the minimum split duration; (3) the merge: adjacent segments with the same pitch-class set AND the same bass pitch class join, not across a barline unless configured. A stretch with nothing sounding produces no segment, and silence keeps the segments either side of it apart.
  - **Bass change rules.** A bass change is a change of pitch class, so an octave leap does not split. It is made by an attack: a bass that changes only because the lowest note releases does not split. The new bass must last at least the minimum split duration within the beat, measured from its attack to the next bass change or the end of the beat, so every piece a split makes is at least that long. A bass attack after silence in the beat counts as a change from no bass.
  - **Config.** `AdaptiveSegmentationConfig`: `min_split_numerator` / `min_split_denominator`, the minimum split duration as a fraction of a beat (default 1/2), and `merge_across_barlines` (default false). `adaptive_segmentation_config_default()` returns these; passing NULL uses them. A denominator of 0, or a minimum above a whole beat, is `AD_SEGMENTATION_ERR_BAD_CONFIG`.
  - **Exact and checked.** All time arithmetic is exact rational and checked: `AD_SEGMENTATION_ERR_OVERFLOW` rather than a wrapped value.
  - **Known limits.** No voice awareness: a segment is every sounding note, whatever its voice. No harmonic-rhythm inference beyond the bass: a chord change under a repeated bass is not found, and the bass is read from pitch alone. Arpeggiation within a beat merges across beats only when the pitch-class content and bass match, and a moving bass (a monophonic arpeggio) splits the beat at each new bass note that lasts long enough. A bass that changes by release is not split. Non-chord tones are not filtered, so a passing tone in the bass can split a beat. Evaluation against hand-marked chord changes in Bach 114 is `frameworks/standard-meter/tests/test_adaptive_segmentation_eval.c`; its marks (`tests/fixtures/annotations/bach114_chord_changes.txt`) are a draft not yet checked against the score, and the file's 4/4 meter is wrong for the 3/4 piece, so the test uses a hand-built 3/4 map.
- `NonChordTone` is a plain enum value naming a figure that embellishes the notes a melody moves between with a dissonant note: passing (steps through a third or more in one direction), neighbor (steps away and back), double neighbor (the upper and lower neighbors in turn), changing tone (the nota cambiata, a five-note figure that outlines a step and leaps from its dissonance), suspension (a note held over from a consonance into a dissonance on a stronger beat, which resolves by stepping down), anticipation (a note that sounds the pitch of the note after it, on a weaker beat before it), appoggiatura (approached by leap, left by step in the opposite direction, typically on a stronger beat), escape tone (approached by step, left by leap in the opposite direction, typically on a weaker beat), retardation (like a suspension but resolving by stepping up), and pedal (a static note, often in the bass, held under chord changes that do not include it). It carries no `EntityID`, pitches, or framework claim. `non_chord_tone_involves_leap` is true for the double neighbor, changing tone, appoggiatura, and escape tone, and `non_chord_tone_involves_static_note` for the suspension, anticipation, retardation, and pedal. Whether a figure is allowed, on which beats, and against what is a convention of a framework (`frameworks/standard-counterpoint`).
- `ImitationAnswer` is a plain enum value naming how a later entry of a melody answers an earlier one in imitative writing: real (every interval kept at a fixed transposition), tonal (adjusted by a step to stay in the key), or free (keeps the rhythm and opening shape, then goes its own way). `imitation_answer_keeps_intervals` is true only for the real answer. It carries no `EntityID`, pitches, or framework claim. Which answer a style expects, and how closely it is kept, is a convention of a framework (`frameworks/sixteenth-century-style`).
- `FugueRole` is a plain enum value naming the part a passage of one voice plays in a fugue: subject (the main theme), answer (a transposition of it, sometimes altered), countersubject (a line sounded with the subject or answer), free counterpoint (an accompanying part that need not recur), link (a short interpolation between entries), or episode (a longer passage between statements). `fugue_role_is_entry` is true for the subject and the answer. It carries no `EntityID`, pitches, or framework claim. Which roles appear where is a convention of a framework (`frameworks/high-baroque-fugue`).
- `OstinatoType` is a plain enum value naming the kind of repeating pattern a work or section is built on, from broad to specific: ostinato (any pattern that repeats throughout in one voice), ground bass (an ostinato in the bass), chaconne, and passacaglia (the Baroque sub-genres of the ground bass, in triple meter). `ostinato_type_is_ground_bass` is true for the ground bass, chaconne, and passacaglia, and `ostinato_type_is_triple_meter_form` for the last two. It carries no `EntityID`, pitches, or framework claim. What a framework asks of each kind is its own convention (`frameworks/baroque-ground-bass`).
- `ImitativeRole` is a plain enum value naming the part a voice plays in an imitation: dux (the leader, which states the melody first) or comes (the follower, which imitates it). It carries no `EntityID`, pitches, or framework claim, and is neither `ImitationAnswer` (how closely an entry follows) nor `FugueRole` (the part a passage plays in a fugue).
- `SchemaFunction` is a plain enum value naming where a Galant schema typically appears in a piece, in the order they occur: opening gambit (to start a piece), continuation (after an opening, as a response to it or to carry the music on: the answer, process, and transition schemas), pre-cadential (just before the cadence, to lead into it), cadence (to conclude), or post-cadential (after the cadence). It carries no `EntityID`, pitches, or framework claim. Which schemas have which function is a convention of a framework (`frameworks/galant-schemas`).
- `ScaleDirection` is a plain enum value naming the direction a scale or a bass line runs: ascending or descending. `scale_direction_opposite` gives the other. It carries no `EntityID`, pitches, or framework claim, and is not `ContourDirection` (`semantics/contour.h`), which also has a "same" direction and describes the change between two pitches of a `Contour`.
- `SequenceKind` is a plain enum value naming a kind of sequential harmonization of a bass scale, a pattern of one or more harmonies that repeats in the direction of the scale: parallel chords, 5-6, 7-6 (a chain of suspensions), cycle of fifths, or 2-3 (the inversion of the 7-6, also a chain of suspensions; `sequence_kind_is_suspension_chain` is true for these two). It carries no `EntityID`, pitches, or framework claim. Which patterns a framework encodes, and their intervals above the bass, are its own convention (`frameworks/scale-harmonization`).
- `HarmonicFunction` is a plain enum value naming the role a chord plays in the flow of a phrase, in the order the functions usually occur: tonic (stable, home), predominant (transitions away from tonic toward dominant), or dominant (urgency to resolve to tonic). It carries no `EntityID`, chord, or framework claim. Which chords have which function, and whether a predominant is strong or weak, is a convention of a framework (`frameworks/standard-harmony`).
- `CadenceType` is the single cadence vocabulary, a plain enum value naming the kind of cadence that ends a phrase: perfect authentic (V to I, both root position, do in the soprano), imperfect authentic (V to I otherwise), half (the phrase ends on V), subverted (a potential cadence avoided because what follows repeats material from the middle of the phrase), plagal (IV to I), deceptive (V to something other than I), authentic unspecified (V to I, PAC versus IAC not decided), and unknown (no type could be determined; never ranked). `cadence_type_is_authentic` is true for perfect and imperfect authentic only. `cadence_type_label` gives a display and debug string only: compare `CadenceType` values, never labels. It carries no `EntityID`, chords, or framework claim, and it is not the `Cadence` structure. Which progressions and melodies make each type, and how strong each is (`harmony_cadence_strength`), are conventions of a framework (`frameworks/standard-harmony`), the one owner of cadence strength order; analysis code receives that order from its caller as a ranking function (see `docs/modules/analysis.md`).
- `SeventhResolution` is a plain enum value naming a way a dominant seventh chord resolves to tonic in four voices: default (every active note resolves by its tendency, leaving a tonic with three roots and one third), incomplete (the fifth is omitted from the V7 and its root doubled), or leading-tone drop (the leading tone of a complete V7 leaps down to sol in an inner voice). `seventh_resolution_gives_complete_tonic` is true for the last two. It carries no `EntityID`, pitches, or framework claim. Which voicings make each resolution is a convention of a framework (`frameworks/standard-harmony`).
- `PhraseModelLabel` is a plain enum value naming the role a chord plays in the phrase model, where each phrase gets one set of the labels Tb, PD, D, Te: tonic beginning (the tonic that starts the phrase), predominant (the first strong predominant just before the cadential dominant), dominant (the cadential V or V7), and tonic ending (the tonic of an authentic cadence, none for a half cadence). `phrase_model_label_abbreviation` gives the short form. It carries no `EntityID`, chord, or framework claim, and it is not `HarmonicFunction`, which says what kind of chord something is wherever it stands. Where each label goes is a convention of a framework (`frameworks/standard-harmony`).
- `SixFourType` is a plain enum value naming the kind of a 6/4 chord (a triad in second inversion, which has a dissonance with the bass): cadential (an embellishment of V(7) over sol in the bass, on a stronger beat than its resolution), passing (built on a passing tone in the bass, between two chords of the same function), neighbor (over a static bass, with upper neighbor motion in two upper voices, between the same root position chord; also called pedal), or arpeggiating (the bass leaps to the fifth of a chord while the upper voices sustain it). `six_four_type_is_labeled` is true for the first three, since the arpeggiating 6/4 is typically not labeled in analysis. It carries no `EntityID`, chord, or framework claim. What makes each kind is a convention of a framework (`frameworks/standard-harmony`).
- `AppliedChordKind` is a plain enum value naming the kind of an applied chord, a chromatic chord that tonicizes a non-tonic chord, making it temporarily sound like tonic: secondary dominant (an applied V or V7) or secondary leading-tone (an applied vii diminished, vii diminished 7, or rarely vii half diminished 7). In analysis the label is the kind followed by the chord being tonicized, with a slash: V7/V is read "five seven of five". It carries no `EntityID`, chord, or framework claim. Which chords can be tonicized, and how an applied chord is spelled and resolved, are conventions of a framework (`frameworks/standard-harmony`).
- `ModulationKind` is a plain enum value naming how a composer introduces a new key in a modulation, a longer-term change of tonic: direct (an abrupt change, often at a phrase boundary; also called a phrase modulation) or pivot (through a pivot chord, a single chord diatonic in both the old key and the new key, labeled with both Roman numerals). It carries no `EntityID`, key, or framework claim. What counts as a pivot chord, and which keys are closely related, are conventions of a framework (`frameworks/standard-harmony`).
- `KeyChangeExtent` is a plain enum value naming how far a passage goes toward a new key, a spectrum from tonicization to modulation by the length of the passage and the strength with which the new key is established: tonicization, extended tonicization (longer than two chords but with no cadence in the new key), weak modulation (a cadence establishes the new key but the passage goes right back to the home key), or modulation (a cadence establishes it and the passage continues in it). `key_change_extent_is_modulation` is true for the last two. It carries no `EntityID`, key, or framework claim. The thresholds are a convention of a framework (`frameworks/standard-harmony`), and an analysis represents a hearing of the passage, not a fact.

## Deferred

Nothing at this layer -- `Scale` and `Contour` were the last two `semantics` gaps and are now built above.

## Dependencies

Depends on `identity` (L0), `core` (L1), `time`/`pitch` (L2), `events` (L3), `containers` (L4), and `structure` (L5) only. Never imports `context`, `relationship`, or `interpretation`.
