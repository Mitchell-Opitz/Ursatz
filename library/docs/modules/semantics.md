# semantics

[Docs index](../README.md): the Ursatz docs by topic.

Layer L6 (`music-semantics`). Path `src/semantics/`, tests `tests/semantics/`. One of four L6 siblings; see `docs/modules/l6-notes.md` for rules shared across all four.

## Provides

`Interval`, `Sonority`, `SonorityBuilder`, `RhythmicPattern`, `Scale`, `Contour`, and the neutral analysis input types below.

Vocabulary enums that stay here (plain names, no `EntityID`, no framework claim; see `docs/vocabulary-enums.md` for the admission rule). An enum used by one framework lives in that framework; one stays only if two or more frameworks, or kernel code, use it:

- Shared by two or more frameworks: `VoicePart` (high-baroque-fugue, standard-harmony, standard-voicing), `BeatStrength` (common-practice-minimal, galant-schemas, standard-counterpoint, standard-harmony, standard-meter), `NonChordTone` (common-practice-minimal, standard-counterpoint, standard-harmony), `AppliedChordKind` (standard-harmony, standard-tonality), `KeyChangeExtent` (common-practice-minimal, standard-harmony).
- Used by kernel code: `CadenceType` (`src/analysis`), `FormLevel` (`src/containers/idea.h`, `subphrase.h`), `SubphraseRole` (`src/containers/subphrase.h`).
- No consumer yet: `ExpectedLengthBasis`.

Moved out: `CounterpointSpecies` and `ImitationAnswer` (`frameworks/standard-counterpoint`, `ImitationAnswer` there because high-baroque-fugue and sixteenth-century-style both depend on it), `FugueRole` (`frameworks/high-baroque-fugue`), `OstinatoType` and `ImitativeRole` (`frameworks/baroque-ground-bass`), `SchemaFunction` (`frameworks/galant-schemas`), `ScaleDirection` and `SequenceKind` (`frameworks/scale-harmonization`), and `MotiveKind`, `PhraseRole`, `PhraseBeginning`, `PhraseEnding`, `IdeaLabel`, `ContinuationTrait`, `PhraseLevelForm`, `PhraseLengthChange`, `ExpansionPlacement`, `InternalExpansionTechnique`, `AlternativePathKind`, `ExternalExpansionKind` (`frameworks/standard-form`).

## Neutral analysis input types

One set of plain types that framework adapters accept (R-242). All pointers are borrowed.

- `AnalysisNote` (`analysis_note.h`): id, optional `NoteEvent`, span, `midi` (C4 = 60, or `ANALYSIS_PITCH_UNKNOWN`), optional spelling and voice id, track and voice (or `ANALYSIS_INDEX_NONE`), voice confidence in [0, 1]. `AnalysisNoteSet` is a note run sorted by `analysis_note_compare` with its `MeterMap`; `analysis_note_valid` and `analysis_note_set_valid` check them.
- `AnalysisSegment` (`analysis_segment.h`): id, span, optional metrical position, beat strength.
- `AnalysisKey` and `AnalysisKeyEvent` (`analysis_key.h`): tonic letter and accidental, major or minor (`KeyStructureMode`, so `semantics/` includes `interpretation/key.h`, the one allowlisted L6 exception). `analysis_key_from_fifths` reads a key signature.
- `AnalysisVoiceGrid` and `AnalysisVoiceCell` (`voice_grid.h`): each voice's note in each segment, row-major by segment, voice 0 the top voice. The harmony and counterpoint adapters' grids are typedefs of it.

## Notes

- `Interval` and `Sonority` do not depend on `PitchClass`. `PitchClass`, `PitchRealization`, and `TuningSystem` now exist (`pitch`, L2 -- see `docs/modules/pitch.md`), but neither of those two types consumes them: `Interval` computes nothing itself, since `PitchIdentity` is an opaque token with no numeric semantics; each of `Interval`'s three dimensions (directed, undirected, chromatic distance) is supplied by the caller as an independently-optional field, never defaulted to zero when unknown. Diatonic distance (the fourth TDD §67 dimension) is not represented at all; wiring it up would need `PitchClass`, which neither type has done. `Scale`, below, is the first type in this module to consume `pitch/pitch_class.h` and `pitch/tuning_system.h`.
- `Sonority` is not a `Chord`. `sonority.h` carries no chord-identification logic (root, quality, inversion); that is `Chord` (`interpretation`, L6, built on top of `Interpretation`).
- `RhythmicPattern` has no pitch fields. `rhythmic_pattern.h` takes no dependency on pitch headers; a rhythmic query never needs pitch information.
- `Scale` is a Value (no `EntityID` of its own, same as `Sonority`): an ordered collection of `PitchClass` (owned, `pitch_class_count > 0`) under a `TuningSystem`, referenced by `EntityID` rather than embedded -- the same reference-only pattern `Sonority`'s `voice_ids` already uses. `Scale` has no `FrameworkReference`: an ordered `PitchClass` collection under a `TuningSystem` does not require an interpretive claim to exist. Contrast `ScaleDegree` (`interpretation/scale_degree.h`), which references a `Scale` and does carry one.
- `Contour` is a Value: a relative pitch-change sequence (`ContourDirection`: up/down/same) over a `PitchIdentity` sequence. Directions are caller-supplied, not computed -- the same principle `Interval` already establishes, since `PitchIdentity` carries no numeric semantics this module could derive a direction from. `Contour` has no `FrameworkReference`: an observed pitch-direction sequence does not require an interpretive claim to exist.
- `SonorityBuilder` (`semantics/sonority_builder.h`) derives `Sonority` objects from raw `NoteEvent`s, closing the gap chord identification (`chain_subset_chord_analyze`, `ursatz_chain/subset_chord_analyzer.h`) previously left on the caller: nothing in this codebase grouped sequential/arpeggiated notes into a `Sonority` before this. Each `NoteEvent`'s onset-to-release activity interval `[onset, onset + duration)` -- left-closed/right-open, the same boundary treatment `TIME_SPAN_BOUNDARY_LEFT_CLOSED` already uses -- is queryable via `sonority_builder_note_active_at` (System Registry Problem A's onset-to-release tracking). The grid-sampling step itself groups notes by ATTACK rather than by that full active span: each beat's `Sonority` is formed from every note whose onset falls within that beat's half-open window, on a FIXED one-sample-per-beat grid hardcoded to a quarter note. Grouping by onset rather than by full sustained activity is a deliberate, empirically-driven choice (validated against the fixture below): a note's duration commonly exceeds one beat in this repertoire (e.g. a held bass tone under faster-moving upper voices), and carrying it forward by sustain into every later beat it still rings through would contaminate each of those beats' `Sonority` with a stale tone instead of that beat's own attack content. This is a stated v1 default (System Registry Problem A: sampling at a fixed metric grid), not a general/adaptive harmonic-rhythm detector (Problem B) -- it does not infer chord-change points, does not vary its grid by texture or tempo, and the beat unit is not a parameter, the same fixed-constant-not-`config`-driven treatment `PhraseBoundaryDetection`'s `max_length_without_cadence` and `SentenceDetection`'s min-2-events continuation floor already use in `docs/modules/analysis.md`. Non-chord-tone tolerance and multi-voice/dense-texture handling (Problem B) are explicitly deferred: every note onsetting within a beat is included as-is, with no best-fit/passing-tone filtering -- `chain/tests/test_bach_prelude_arpeggiated_chords.c` accounts for this by treating a measure as matching its expected chord when AT LEAST ONE of its four beat-grid `Sonority`s resolves to it, rather than requiring every beat's (possibly non-chord-tone-contaminated) sample to agree. Built and validated against solo/monophonic-texture writing only (`tests/fixtures/arpeggiation-investigation/Bach_Prelude_C_Major.mid`). A beat with no note onsetting in it produces no `Sonority` (`Sonority` requires `event_id_count > 0`) -- silence between attacks is a legitimate gap, not an error.
- `VoicePart` is a plain enum value (soprano, alto, tenor, bass, ordered highest to lowest) naming a role in a four-part texture. It carries no `EntityID`, range, clef, or framework claim, and it is not `Voice` (`containers/voice.h`), which identifies a single line and may be written as any part or none. Ranges, staves, and stems for each part are conventions of `frameworks/standard-voicing`.
- `BeatStrength` is a plain enum value naming the metric weight of a position in a bar: strong, medium, or weak, ordered from strongest to weakest so a smaller value is a stronger position. It carries no `EntityID`, time signature, or framework claim, and it is not the beat grid of a time signature (`time/time_signature.h`). Which positions of a bar have which strength is a convention of a framework (`frameworks/standard-counterpoint`): in two notes against one, the first note of each bar is strong and the second weak; in four notes against one, the four notes are strong, weak, medium, weak.
- **Adaptive sonority segmentation** (`semantics/sonority_segmentation.h`): a second, meter-aware way to cut notes into `Sonority` segments, `sonority_builder_build_adaptive`, next to the fixed-grid `SonorityBuilder`. The fixed-grid builder is unchanged (Analyzer, GUI and the existing tests use it, and callers move over later); this one does not group by attack on a quarter-note grid, ignore meter, or drop a note held into a later beat.
  - **Membership.** A segment holds every note SOUNDING in it, those attacked in the segment and those held over from earlier. `AdaptiveSonority` is the `Sonority` (its `time_window` is the segment's `[start, end)`, left-closed; event ids are clones of the notes' ids, in input order; no voice restriction; domain SOUNDING) plus `held[i]`, parallel to the event ids: true if the note was sounding before the segment began. `Sonority` itself is unchanged, since attacked-versus-held is segmentation metadata and not part of a selection's identity. Weighting by duration or metric position is not done here (that is the chord-identification work). The bass of a segment is its lowest sounding pitch.
  - **Pitch.** Pitch comes from each note's `PitchSpelling` as a semitone number (`12 * (octave + 1)` plus the letter's semitone plus the accidental, so C4 is 60); the pitch class is that mod 12. A note with no spelling is `AD_SEGMENTATION_ERR_NO_PITCH`, not skipped. The MIDI importer always sets one.
  - **Injected beat grid.** The beat grid is a `BeatGridProvider` the caller passes: a function that returns the beat starts of one measure of a `MeterMap`. The kernel cannot include a framework, so what a beat is arrives by injection, the same pattern the cadence ranking uses. `frameworks/standard-meter` supplies the standard provider (`standard_meter_segmentation_beat_grid`): 6/8 gives two dotted-quarter beats, 3/4 three quarter-note beats, 12/8 four dotted-quarter beats, and 5/8 five eighth-note pulses. A short measure is laid out from its own start and its last beat is cut at the barline; a pickup measure uses its offset from where a full measure would have started, so its beats fall where the full measure's would.
  - **The three steps**, in order, each its own internal function with its own tests: (1) the grid cut: one segment per beat of every measure up to the end of the last sounding note; (2) the bass split: a beat splits at the attack of a new lowest note, unless the new bass lasts less than the minimum split duration; (3) the merge: adjacent segments with the same pitch-class set AND the same bass pitch class join, not across a barline unless configured. A stretch with nothing sounding produces no segment, and silence keeps the segments either side of it apart.
  - **Bass change rules.** A bass change is a change of pitch class, so an octave leap does not split. It is made by an attack: a bass that changes only because the lowest note releases does not split. The new bass must last at least the minimum split duration within the beat, measured from its attack to the next bass change or the end of the beat, so every piece a split makes is at least that long. A bass attack after silence in the beat counts as a change from no bass.
  - **Config.** `AdaptiveSegmentationConfig`: `min_split_numerator` / `min_split_denominator`, the minimum split duration as a fraction of a beat (default 1/2), and `merge_across_barlines` (default false). `adaptive_segmentation_config_default()` returns these; passing NULL uses them. A denominator of 0, or a minimum above a whole beat, is `AD_SEGMENTATION_ERR_BAD_CONFIG`.
  - **Exact and checked.** All time arithmetic is exact rational and checked: `AD_SEGMENTATION_ERR_OVERFLOW` rather than a wrapped value.
  - **Known limits.** No voice awareness: a segment is every sounding note, whatever its voice. No harmonic-rhythm inference beyond the bass: a chord change under a repeated bass is not found, and the bass is read from pitch alone. Arpeggiation within a beat merges across beats only when the pitch-class content and bass match, and a moving bass (a monophonic arpeggio) splits the beat at each new bass note that lasts long enough. A bass that changes by release is not split. Non-chord tones are not filtered, so a passing tone in the bass can split a beat. Measured against hand-marked chord changes in Bach 114 (measures 1-16, 36 marks, within an eighth note) the segmenter has recall 1.00 and precision 0.51: every marked change has a boundary, but about half the boundaries are extra, because the merge step compares the whole sounding pitch-class set and the bass, so a melody note or a passing bass note over an unchanged harmony keeps a beat-level cut. Precision is reported, not asserted. The evaluation is `frameworks/standard-meter/tests/test_adaptive_segmentation_eval.c`; its marks (`tests/fixtures/annotations/bach114_chord_changes.txt`) are a draft not yet checked against the score, and the file's 4/4 meter is wrong for the 3/4 piece, so the test uses a hand-built 3/4 map.
- `NonChordTone` is a plain enum value naming a figure that embellishes the notes a melody moves between with a dissonant note: passing (steps through a third or more in one direction), neighbor (steps away and back), double neighbor (the upper and lower neighbors in turn), changing tone (the nota cambiata, a five-note figure that outlines a step and leaps from its dissonance), suspension (a note held over from a consonance into a dissonance on a stronger beat, which resolves by stepping down), anticipation (a note that sounds the pitch of the note after it, on a weaker beat before it), appoggiatura (approached by leap, left by step in the opposite direction, typically on a stronger beat), escape tone (approached by step, left by leap in the opposite direction, typically on a weaker beat), retardation (like a suspension but resolving by stepping up), and pedal (a static note, often in the bass, held under chord changes that do not include it). It carries no `EntityID`, pitches, or framework claim. `non_chord_tone_involves_leap` is true for the double neighbor, changing tone, appoggiatura, and escape tone, and `non_chord_tone_involves_static_note` for the suspension, anticipation, retardation, and pedal. Whether a figure is allowed, on which beats, and against what is a convention of a framework (`frameworks/standard-counterpoint`).
- `CadenceType` is the single cadence vocabulary, a plain enum value naming the kind of cadence that ends a phrase: perfect authentic (V to I, both root position, do in the soprano), imperfect authentic (V to I otherwise), half (the phrase ends on V), subverted (a potential cadence avoided because what follows repeats material from the middle of the phrase), plagal (IV to I), deceptive (V to something other than I), authentic unspecified (V to I, PAC versus IAC not decided), and unknown (no type could be determined; never ranked). `cadence_type_is_authentic` is true for perfect and imperfect authentic only. `cadence_type_label` gives a display and debug string only: compare `CadenceType` values, never labels. It carries no `EntityID`, chords, or framework claim, and it is not the `Cadence` structure. Which progressions and melodies make each type, and how strong each is (`harmony_cadence_strength`), are conventions of a framework (`frameworks/standard-harmony`), the one owner of cadence strength order; analysis code receives that order from its caller as a ranking function (see `docs/modules/analysis.md`).
- `MotiveOccurrenceKind` (`motive_occurrence_kind.h`) is the one vocabulary for how a motive recurrence reads against its prototype: exact, real-transposed, tonal-transposed, inverted, retrograde, augmented, diminished, fragmented, varied. A plain enum with `motive_occurrence_kind_name`, `_rank` (the precedence when several apply, lower wins) and `_valid`. It is not the operations that make a motive: those are `MotiveRelationKind` (`analysis/motive_relation.h`, L8), and a caller maps the relation it finds to an occurrence kind. VARIED has no relation; it is standard-form's own reading.
- `AppliedChordKind` is a plain enum value naming the kind of an applied chord, a chromatic chord that tonicizes a non-tonic chord, making it temporarily sound like tonic: secondary dominant (an applied V or V7) or secondary leading-tone (an applied vii diminished, vii diminished 7, or rarely vii half diminished 7). In analysis the label is the kind followed by the chord being tonicized, with a slash: V7/V is read "five seven of five". It carries no `EntityID`, chord, or framework claim. Which chords can be tonicized, and how an applied chord is spelled and resolved, are conventions of a framework (`frameworks/standard-harmony`).
- `KeyChangeExtent` is a plain enum value naming how far a passage goes toward a new key, a spectrum from tonicization to modulation by the length of the passage and the strength with which the new key is established: tonicization, extended tonicization (longer than two chords but with no cadence in the new key), weak modulation (a cadence establishes the new key but the passage goes right back to the home key), or modulation (a cadence establishes it and the passage continues in it). `key_change_extent_is_modulation` is true for the last two. It carries no `EntityID`, key, or framework claim. The thresholds are a convention of a framework (`frameworks/standard-harmony`), and an analysis represents a hearing of the passage, not a fact.

## Deferred

Nothing at this layer -- `Scale` and `Contour` were the last two `semantics` gaps and are now built above.

## Dependencies

Depends on `identity` (L0), `core` (L1), `time`/`pitch` (L2), `events` (L3), `containers` (L4), and `structure` (L5) only. Never imports `context`, `relationship`, or `interpretation`.
