# io

[Docs index](../README.md): the Ursatz docs by topic.

Layer L9 (`music-io`). Path `io/`, tests `tests/io/`. Depends on `identity`, `core`, `time`, `pitch`, and `events` only (and, for `movement_export`, the `realization` group) (and, for `MusicXMLImporter`, the XML parser vendored in the repository's `third_party/ezxml/`, which nothing else may use). Must not depend on `containers` (L4) or anything above it, and must not depend on `theory`, `rules`, `transform`, `analysis`, `generation`, `theory/`, or `music-analysis`.

## Provides
- `MIDIImporter` (`midi_importer_import_complete`): parses an SMF type 0 or 1 buffer once into time-ordered `NoteEvent`s (L3) with the file's meter, tempo, key signatures, track names and program changes. `MIDIRenderer` (`midi_renderer.h`, `docs/modules/midi_renderer.md`) writes them back. MusicXML export is in `io/`. See [io-midi.md](io-midi.md).
- `movement_export_midi` and `movement_export_musicxml` (`movement_export.h`, R-599): a `Movement`'s performer parts (`realization/`) as a Standard MIDI File and a MusicXML document, through the renderer and the MusicXML writer (the writer prints a `ScoreLayout`, `io/score_layout.h`, which a caller may read instead of the XML: [export.md](export.md)). `io` now uses the `realization` group. One NoteEvent is made per performer note (its id is the note's id, so it is the MusicXML `xml:id`; its voice is `<part id>-v<voice>`); MIDI writes one track per part with a program change on each channel and the sustain pedal as controller 64 (the division is 480 when every time is a whole tick, else the smallest that works); MusicXML writes one part per performer part, its staves, the pedal under the part's last staff and the work's title and composer. A movement with played spans is refused (`MOVEMENT_EXPORT_ERR_NOT_BUILT`), one with no notes too (`_NO_NOTES`). Details: [midi_renderer.md](midi_renderer.md#performer-part-tracks-r-599), [export.md](export.md).
- `MusicXMLImporter` (`musicxml_importer.h`): an uncompressed score-partwise document into the same canonical outputs. See [io-musicxml.md](io-musicxml.md).
- The imported score (`imported_score.h`, R-614): `imported_score_import_file` and `imported_score_import_buffer` read a MIDI or MusicXML document (chosen by `ImportedFormat`, or detected from the extension and the first bytes) into one `ImportedScore` whatever the format: the notes with their pitch values and streams, the meter map, the key signature events, the tempo map (MIDI), the parts, staves, tempo markings and dynamics (`Rational` times), and what the input says about itself (`ImportedSource`). The buffer entry makes no temporary file. The library prints nothing: a failure is an `ImportedScoreResult` with a message in `ImportedScoreError`, and the importer's warnings are lines in `source.warnings` that the caller shows. `imported_reading_apply` rescales a score by a reading (a meter, a pickup, a scale), `imported_score_view` builds a score from events somebody else owns (a Composer fragment; its events and a given meter map are borrowed), and `imported_score_destroy` releases it. The General MIDI names of the parts come from `general_midi.h` (private).

The neutral notes the analysis chain and the framework adapters read (`analysis/notes/analysis_note.h`, R-242) are made from an import by the one builder `analysis_note_set_build` (`analysis/notes/analysis_note_build.h`, R-614): the Analyzer's chain input and the library test helper `tests/import_notes_test_util.h` (`midi_import_analysis_notes`, `musicxml_import_analysis_notes`) both call it.

## Notes

- `MIDIImporter` is built from three internal pieces: `smf_reader` (byte-level SMF header/track chunk parsing), `midi_event_decoder` (walks one track's decoded bytes once and extracts note-on/note-off events, program changes, the track name, time signatures and tempos, including running status), and `midi_importer` itself (matches note-on/note-off pairs, converts to `NoteEvent`, flattens and time-orders across tracks). Only `midi_importer.h` is a public entry point; `smf_reader` and `midi_event_decoder` are implementation detail.
- **Tempo-independent units.** The notes do not depend on the tempo meta-events (the import returns them as a `TempoMap`, separately), and no tempo is assumed. `MusicalTime`/`Duration` are produced as an exact whole-note fraction derived from tick counts and the header's ticks-per-quarter-note (PPQN) division field alone: a quarter note is `PPQN` ticks, a whole note is `4 * PPQN` ticks, so a tick position/duration becomes `numerator = ticks`, `denominator = 4 * PPQN` (exact rational, Law 19). No BPM/seconds conversion is performed -- the same tick count always yields the same `Duration` regardless of tempo, since PPQN is fixed per file and a tick carries no tempo information of its own until combined with a tempo meta-event (not read here). A file with an actual tempo map still has no real-world playback duration recovered by this importer; that remains a deliberate scope cut (see Deferred), it just no longer means `Duration` itself is tempo-dependent.
- SMPTE-format division (the header's division field with its top bit set) is rejected as malformed rather than decoded -- consistent with "fail cleanly on anything not a well-formed SMF 0/1 file" rather than attempting best-effort support.
- Note-on/note-off pairing is done independently per track (MIDI convention: a note-on and its matching note-off always live in the same track), matching each note-on to the earliest following unmatched note-off with the same channel and note number. An unmatched note-on at the end of a track (no corresponding note-off) is treated as a malformed file and fails cleanly, rather than being inferred as ending at track end.
- **Provenance.** This is likely the first real, populated (non-test) use of `ProvenanceReference` (`core`, L1) in this codebase. No `ProvenanceActivity`/`ProvenanceAgent` type exists yet anywhere in the codebase -- that is legitimate future work, scoped separately, not a silent addition here. Instead, `MIDIImporter` constructs one stable `EntityID`, `"midi-importer-v1"`, and every `NoteEvent` it produces points its `ProvenanceReference` at that same id.
- Pitch conversion goes through the existing `PitchNumericValue` → `PitchIdentity` path (`pitch_numeric_value_create` + `pitch_numeric_value_to_identity`), under one importer-local `TuningSystem` labeled `"MIDI note number"` -- a plain linear space where a `PitchNumericValue` position of N means "MIDI note number N," with no 12-TET or A440 assumption baked in beyond what the MIDI note number itself already is. No parallel pitch-conversion path was introduced.
- **PitchSpelling.** Every `NoteEvent` also gets a `PitchSpelling` (letter, accidental, octave), set on `optional_pitch_spelling`. A MIDI note number carries no key context, so this importer always spells the 5 black-key pitch classes as the sharp of the letter below (accidental = 1) rather than the flat of the letter above -- e.g. MIDI note 61 is always spelled C#, never Db. This is a fixed, key-signature-unaware convention, not a general enharmonic-spelling model; nothing elsewhere in the codebase spelled pitches before this. Octave follows the standard MIDI convention (`octave = note / 12 - 1`, so MIDI 60 = C4).
- **Numeric pitch output.** `midi_importer_import_complete` also returns the `PitchNumericValue` it computed for each `NoteEvent`, via a second output array (`pitch_values`) index-paired with the `NoteEvent` array (same count, same order). This exists because `PitchIdentity`'s conversion is intentionally one-directional (see `pitch/pitch_numeric_value.h`) -- there is no way to recover a numeric pitch from a `NoteEvent`'s opaque `PitchIdentity` after the fact, so a caller needing numeric pitch data (e.g. for chord/key analysis) has no source for it other than this importer exposing the value it already computed. `midi_import_destroy` releases the array and every `PitchNumericValue` in it. This does not weaken or bypass `PitchIdentity`'s opacity guarantee in any way -- it is a plain by-product of this importer's own MIDI-note-number tuning system, exposed only for the `NoteEvent`s this importer itself produced.

## Deferred

Deliberate scope cuts for `MIDIImporter`, not gaps to be filled incidentally:

- The notes are not changed by tempo meta-events; the import returns them as a `TempoMap`. MIDI rendering or export, `MetronomeMarking`/`TempoMarking` from MIDI tempo, and tempo or rubato inference from note timing are not done.
- The notes are not changed by time signature meta-events; the import returns them as a `MeterMap`. Beats, subdivisions and beat strength are not computed, and no meter or pickup is inferred from note content.
- Every Key Signature meta-event is returned, in time order. Deciding a key or detecting a modulation from them is analysis work, not done here.
- Controller (CC), pedal, program change, pitch bend, and aftertouch events are ignored, not errored on.
- Channel-aware `Voice` assignment is not attempted: channels inside one track share that track's voice slots. Every import (R-386; before, a file whose notes lay on more than one channel got no voice) gets a `VoiceReference` assigned per `NoteEvent` via greedy interval-graph coloring by timing, scoped independently within each source track, purely so `MusicXmlExport` (`music-export`) can represent overlapping notes (e.g. two-handed piano recorded onto one track/channel, or a two-staff piece with RH/LH on separate tracks) without a false-positive overlap error. Voice ids are namespaced by track, so two tracks that each land on local slot 0 never collide into the same exported voice. This is an export-grouping label only -- no musical/analytical meaning, no melody/harmony distinction, and it is a placeholder pending Deliverable F (Container and Structure Specification). Voice ids read `midi-voice-<track>-<slot>`. The harmonic span rule for accented tones that resolve by step (R-382) reads them, so a two-channel file such as the Composer's exports carries its voices by track. No backfill: only new imports get this.
- Malformed/unusual header recovery is not attempted. Anything that is not a well-formed SMF type 0 or type 1 file fails cleanly with a defined error, rather than being best-effort recovered.
- SMF type 2 files are rejected as unsupported, not parsed.
- Key-signature-aware spelling (choosing sharps vs. flats per the piece's actual key) is not attempted -- this importer has no key-detection step to draw on, and always applies the fixed sharps-only convention described above.

Out of scope entirely for this module, not missing: renderers, importer formats other than SMF and MusicXML, and `DigitalArtifact`.

## Dependencies

Depends on `identity` (L0), `core` (L1), `time` and `pitch` (L2), and `events` (L3) only. `MeterMap` and `TempoMap` are in `time`; the importer does not depend on `theory/meter` or any framework.
