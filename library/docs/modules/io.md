# io

Layer L9 (`music-io`). Path `src/io/`, tests `tests/io/`. Depends on `identity`, `core`, `time`, `pitch`, and `events` only (and, for `MusicXMLImporter`, the vendored XML parser in `third_party/ezxml`, which nothing else may use). Must not depend on `containers` (L4) or anything above it, and must not depend on `theory`, `rules`, `transform`, `analysis`, `generation`, `frameworks/`, or `music-analysis`.

## Provides

`MIDIImporter`: parses a Standard MIDI File (SMF) type 0 or type 1 buffer into a flat, time-ordered sequence of canonical `NoteEvent`s (L3). `MIDIRenderer` (`midi_renderer.h`, see `docs/modules/midi_renderer.md`) writes the same canonical events back to an SMF. No other importer format (`MusicXMLImporter`, below, is the second), or `DigitalArtifact` type is scaffolded here, even though they are related Registry items for this layer. MusicXML export lives in its own module, `src/export/`.

`midi_key_signature_scan`: a second, standalone entry point that scans an SMF buffer for its first Key Signature meta-event (`0xFF 0x59`) and reports the signed sharps/flats count and major/minor flag it carries. This is intentionally separate from `MIDIImporter` rather than a new output on `midi_importer_import` -- it does not touch note import at all, walking track bytes itself (its own small event-length skipping; the delta-time reader is the shared `midi_event_decoder_read_vlq`) so it can be added without changing `midi_importer_import`'s or `midi_event_decoder_decode`'s signatures or any of their existing callers. A future pass may fold this into `midi_event_decoder`/`midi_importer` proper as a refactor once this path is proven; its consumers are Ursatz-Analyzer's `key_pipeline.c` and Ursatz-GUI's `analysis_service.c`.

`midi_key_signature_scan_all`: reports every Key Signature meta-event in an SMF buffer, with its position, in time order. `midi_key_signature_scan` is kept unchanged for existing callers (Ursatz-Analyzer's `key_pipeline.c`, Ursatz-GUI's `analysis_service.c`) and still reports only the first event; the new function is where key changes are read. It stays separate from `MIDIImporter`, like the first-event scanner.

- **Entry fields.** Each `MidiKeySignatureEvent` carries a `KeySignature` (`pitch/key_signature.h`), a `MidiModeHint`, the position as `MusicalTime`, the raw `tick` and `track_index`, and the raw `sharps_flats` (sf) and `mode_byte` (mi) bytes. The list is owned and released with `midi_key_signature_events_destroy`.
- **KeySignature versus mode hint.** `midi_key_signature_build(sf, &out)` builds the `KeySignature` for an sf value in -7..7 in circle-of-fifths order (sharps F C G D A E B, flats B E A D G C F; sf 0 is empty); out-of-range sf is an error. It is a spelling only and makes no claim about key or mode. The mi byte is a hint carried next to the `KeySignature`, never part of it: `mi` 0 is `MIDI_MODE_HINT_MAJOR`, 1 is `MINOR`, anything else is `UNKNOWN` (the event is kept). Turning sf and mi into a key is analysis work, not done here.
- **Position.** Ticks accumulate per track and convert as `MIDIImporter` does: `MusicalTime = tick / (4 * division)`, an exact whole-note fraction. SMPTE division is rejected as unsupported, and so is a division of 0.
- **Order and duplicates.** Events from all tracks are merged and ordered by tick, then track index, then byte order within a track. An exact duplicate (same tick, same sf, same mi) is reported once, on the lowest track. Different events at the same tick are all kept, in that order.
- **Malformed events and errors.** A malformed `0xFF 0x59` is skipped and scanning continues: a length other than 2, or an sf outside -7..7. Structural SMF errors (null buffer, truncated, bad header, unsupported format or division, bad track) are reported with the same meaning as `midi_key_signature_scan`. A file with no key signature events returns OK with zero entries.
- **Compatibility.** Both functions agree on ordinary files. They can differ on unusual ones: the first-event function takes the first event in track-then-byte order and returns an out-of-range sf as is, while the first entry of the new function is the earliest in time and an out-of-range sf is skipped.

`midi_importer_import_complete`: the public entry point that returns everything the importer reads from one parse. It fills a `MidiImport` (release with `midi_import_destroy`; NULL and a zeroed struct are safe) with the notes and their `PitchNumericValue`s (as `midi_importer_import`), `note_tracks[i]` and `note_channels[i]` (the MTrk index and MIDI channel of note `i`), the `MidiMeterImport`, the `MidiTempoImport`, the `MidiKeySignatureEvents`, the header's `format` and `division`, and one `MidiTrackInfo` per track chunk.

- **One parse, one pass per track.** `smf_reader_parse` runs once and `midi_event_decoder_scan` walks each track once, collecting note events, program changes, the track name, time signatures and set-tempo events together. Key signatures come from the same walk: `midi_key_signature.c` exposes a collector (`midi_key_signature_collector_meta` per meta-event, `_finish` once) that the walk feeds and that `midi_key_signature_scan_all` feeds too, so the key logic exists once.
- **Tracks.** `MidiTrackInfo` has the chunk `index`, the `name` (the first `0xFF 0x03` in the chunk, NULL when absent) and the `programs`: each `0xC0` program change in byte order with its channel, program number (0-127), tick and exact `MusicalTime` (`tick / (4 * division)`). A chunk with no events has a NULL name and no programs.
- **Wrappers.** `midi_importer_import`, `midi_importer_import_with_meter` and `midi_importer_import_with_tempo` keep their signatures and results; each calls the complete import, moves out the part it returns and destroys the rest. Because every part is built, a file whose tempo times would overflow a `TempoMap` (`MIDI_IMPORT_ERR_ALLOC`) now fails in all four, and a division of 0 is `MIDI_IMPORT_ERR_UNSUPPORTED_DIVISION` everywhere.
- **Internal.** `smf_reader.h` and `midi_event_decoder.h` stay implementation details of the module; the one variable-length-quantity reader is `midi_event_decoder_read_vlq`, used by the decoder and the key signature walk. On any failure `*out` is untouched. `tests/io/test_midi_import_complete.c` compares the complete import with the three older entry points and `midi_key_signature_scan_all` on a type 0 and a type 1 fixture and the five corpus files, and runs under valgrind.

`midi_importer_import_with_meter`: the additive way to read a file's meter. `midi_importer_import` is unchanged and still returns only notes, so Ursatz-Analyzer and Ursatz-GUI see no difference. It is a new function rather than a field on the existing result because `MidiImportResult` is a bare status enum with nothing to extend, and changing `midi_importer_import`'s signature would break those callers. It takes the same arguments plus a `MidiMeterImport` and returns the same notes (it runs `midi_importer_import` itself, then reads the meter from the same buffer).

- **MidiMeterImport.** `meter_map` is the file's time signatures as a `MeterMap` (`time/meter_map.h`; measure numbering, the pickup rule and barline ownership are documented there). A file with no `0xFF 0x58` gets a single 4/4 region marked defaulted, so a consumer can tell a declared meter from a default. `end_time` is the time of the last note-off in whole notes (0 with no notes); pass it to `meter_map_measure_count`. `conflict_ticks` lists ticks where different signatures shared a tick. Release with `midi_meter_import_destroy`. On any failure no output is written.
- **Time signature decoding.** `midi_event_decoder_collect_time_signatures` decodes `0xFF 0x58` (length 4, `nn dd cc bb`; `dd` is a power of two, so `6 3` is 6/8) from every track into `TimeSignature`s with a tick position. `cc` and `bb` are not read beyond the length. Events merge in time order (tick, then track, then byte order): an exact duplicate is merged, and if different signatures share a tick the last in track order wins and the tick is reported in `conflict_ticks` (the library prints nothing). Malformed events are skipped, as the key signature scan skips its own: a length other than 4, `nn` outside 1..64, or `dd` above 4 (a bottom number past 16). SMPTE division is rejected as elsewhere. `midi_event_decoder_decode` still skips these events and keeps its signature.
- **Measures follow the file.** Measure numbers come from the file's own time signature events only; no meter or pickup is inferred from note content. A file whose meter disagrees with its score is imported as the file says. Two corpus files show this: `Bach 114.mid` declares 4/4 for a 3/4 minuet (24 measures where the score has 32), and `Mozart 545.mid` holds three movements on one timeline, so it numbers straight through (338) where the score restarts each movement. `Field 1.mid`'s first note sits nine eighths into its first 12/8 measure, the shape of a padded upbeat, which the importer numbers as measure 1 because the file declares no pickup. `tests/io/test_midi_corpus_meter.c` records each case.

`midi_importer_import_with_tempo`: the additive way to read a file's tempo, with the same shape as `midi_importer_import_with_meter`. `midi_importer_import` and `midi_importer_import_with_meter` are unchanged, so Ursatz-Analyzer and Ursatz-GUI see no difference. It takes the same arguments plus a `MidiTempoImport` and returns the same notes (it runs `midi_importer_import` itself, then reads the tempo from the same buffer).

- **Symbolic time stays tempo-independent.** Note positions and durations are whole-note fractions of ticks and the header's division alone, as before. Reading the tempo does not change them, byte for byte (a test compares the notes of both calls). The `TempoMap` answers a separate question, how many seconds a `MusicalTime` is; it is not an input to the notes.
- **MidiTempoImport.** `tempo_map` is the file's set-tempo events as a `TempoMap` (`time/tempo_map.h`; the exact seconds mapping and its inverse are documented there), one region per distinct tick. A tempo at tick 0 is the first region. With none at tick 0 the MIDI default of 500,000 microseconds per quarter note (120 quarter notes per minute) applies from 0 as a defaulted region; a file with no set-tempo event is one defaulted region, so a consumer can tell a declared tempo from a default. `conflict_ticks` lists ticks where different tempos shared a tick. Release with `midi_tempo_import_destroy`. On any failure no output is written; a file whose seconds would overflow a `TempoMap` fails with `MIDI_IMPORT_ERR_ALLOC`.
- **Set-tempo decoding.** `midi_event_decoder_collect_tempos` decodes `0xFF 0x51` (length 3, one big-endian 24-bit value, microseconds per quarter note) with its tick from every track. Events merge in time order (tick, then track, then byte order): an exact duplicate is merged, and if different tempos share a tick the last in track order wins and the tick is reported in `conflict_ticks` (the library prints nothing). A tempo that repeats the previous one at a later tick is kept, so the region list is what the file says. Malformed events are skipped: a length other than 3, or a tempo of 0. SMPTE division is rejected as elsewhere. `midi_event_decoder_decode` still skips these events and keeps its signature.
- **File values, not score values.** The corpus tempos are whatever the files encode. `tests/io/test_midi_corpus_tempo.c` records each piece's first tempo and region count (Field 1 has 602 regions, Mozart 545 has 24) and says so; nothing here infers a tempo or rubato from note timing.

`MusicXMLImporter` (`src/io/musicxml_importer.h`): reads an uncompressed score-partwise MusicXML document into the same canonical outputs as `MIDIImporter` (`NoteEvent`s, a `MeterMap`, a `TempoMap`, key-signature events), so every analysis downstream runs unchanged, and adds what notation carries and MIDI cannot: pitch spelling, parts, staves, notated voices, tempo text and dynamics. An external format is an adapter and defines nothing of the canonical domain (Architecture Principle 14). `musicxml_import_buffer` and `musicxml_import_file` fill a `MusicXmlImport`; `musicxml_import_destroy` releases it. `MIDIImporter` and `MusicXmlExport` are not changed.

- **Supported subset.** Uncompressed `score-partwise` `.musicxml` / `.xml` (UTF-8 or UTF-16, a byte order mark allowed), at most `MUSICXML_IMPORT_MAX_BYTES` (256 MiB). Not read: compressed `.mxl`, `score-timewise` (an error that says so), MEI, ABC.
- **Errors and warnings.** A structural error returns a status and a message in `error_message`, with no notes and nothing to destroy: malformed XML, a root other than `score-partwise`, a duration-bearing element before any `<divisions>`, a value that cannot be read (a `<step>` outside A-G, a missing `<octave>` or `<duration>`, a negative duration), an input over the size limit. Everything else that is skipped, rounded or inconsistent is a warning: `warnings.count` counts them all and the first 16 messages (each starting "part P1, measure 3:") are kept. A warning never stops the import.
- **Time.** A duration of `d` divisions at `D` divisions per quarter note is `d / (4 * D)` whole notes, as an exact rational (`ExactRational`, checked, never floating point). `<divisions>` may change at any point; `<backup>`, `<forward>` and `<chord/>` are handled exactly (a chord note starts where the previous non-chord note started and takes no time). A `<backup>` that would go before the measure start stops at the start, with a warning. The next measure starts where the furthest voice of the last one ended. Tuplet durations are taken as written.
- **Notes, rests, ties.** A rest and a cue note advance time and make no `NoteEvent`. A grace note takes no time and is skipped with a warning. An unpitched note is skipped with a warning and still advances time. A note with a zero duration, or below MIDI 0, is skipped with a warning. A tie start and stop (a `<tie>`, or a `<tied>` notation when there is no `<tie>`) merge into ONE `NoteEvent`, across barlines and in chains, when the same part and voice has the same sounding pitch and the stop starts exactly where the last note ended; a stop that matches no start, and a start that never stops, are warnings.
- **Pitch.** `PitchSpelling` is the written step, alter and octave. The `PitchNumericValue` is the sounding pitch, `12 * (octave + 1) + step + alter + transposition`, under the same `"MIDI note number"` tuning the MIDIImporter uses, and the `NoteEvent`'s `PitchIdentity` is made from it. A fractional `<alter>` is rounded (warning). Cb4 is spelled C-flat and sounds as MIDI 59; B-sharp 3 sounds as 60.
- **Meter.** Each `<time>` gives a `TimeSignature` at its position and the `MeterMap` is built from them, declared, not defaulted. With no `<time>` the map is the defaulted 4/4, as for a MIDI file with none. A first measure marked `implicit="yes"` and shorter than a full measure is the PICKUP, measure 0: the `MeterMap` finds a pickup only from a short first region, so the importer ends the first region at the pickup's length. Additive meters (`3+2`) are summed (warning); `senza-misura`, a `<beat-type>` that is not a power of two, and an unreadable `<time>` are skipped. Several parts that disagree at one position keep the first part's signature (warning). Barlines and measure numbers come from the signatures alone: a measure of the document whose length differs from its signature's, other than an `implicit` one, cannot be represented and is a warning.
- **Keys.** Each `<key>` gives a `MusicXmlKeySignatureEvent`: a `KeySignature` (built by `midi_key_signature_build`), a `MusicXmlModeHint` (`major`, `minor`, or `unknown` for any other mode or none: the mode is a hint beside the signature, never part of it), the position, the raw `sharps_flats` and the part. It has the same shape as a `MidiKeySignatureEvent` without the MIDI-only tick, track and mode byte. Exact repeats (same position, fifths and mode, in other staves or parts) are one event, on the lowest part. A `<fifths>` outside -7..7 is skipped (warning). Deciding a key from these is analysis work, not done here.
- **Parts, staves, voices.** `parts[i]` (document order) has the `<score-part id>`, the `<part-name>` and the `<staves>` count (1 by default). Each note keeps its part index and `<staff>` (1 when none). A notated `<voice>` within a part is a `Voice`: the `NoteEvent` carries a `VoiceReference` whose target id is `musicxml-voice-<part id>-<voice>`, and none when the note names no voice. These are notated voices, not separated ones: the MIDIImporter's per-track voices are unchanged and nothing here separates voices. Note ids are `musicxml-<part id>-<n>`, `n` counting from 0 in document order within the part. Notes come out in time order (stable by onset, part, document order), as the MIDIImporter returns them.
- **Transposing parts.** A `<transpose>` (`<chromatic>` plus 12 * `<octave-change>`) shifts the SOUNDING pitch, the `PitchNumericValue` and `PitchIdentity`; the `PitchSpelling` stays the written pitch. Each distinct transposition of a part is a warning, because downstream analysis reads sounding pitch (a clarinet in B-flat's written C5 sounds as B-flat 4).
- **Tempo.** A `<sound tempo="...">` (quarter notes per minute, in a `<direction>` or on its own in a measure) gives a `TempoMap` region at its position: microseconds per quarter note is 60,000,000 / bpm rounded to the nearest whole microsecond (a `TempoMap` holds whole microseconds), with a warning when it was not exact. A tempo after position 0 leaves the default region before it. Parts that disagree at one position keep the first part's (warning). With no tempo the map is the defaulted 120 quarter notes per minute. A `<metronome>` (beat unit, `<beat-unit-dot/>`s, per-minute) gives a `MetronomeMarking` and a `TempoMarking` at its position, and so does a `<sound tempo>` that has `<words>`. `<words>` are tempo text ONLY when their `<direction>` also holds a `<metronome>` or `<sound tempo>`: io carries no tempo vocabulary, so other direction text ("rit.", "dolce") is not classified and is counted in one warning. A `<metronome>` with no words is a `TempoMarking` with only the metronome marking. A direction's `<offset>` moves a marking, never a `<sound tempo>`.
- **Dynamics.** Each `<dynamics>` child (p, mf, sfz, ...; `<other-dynamics>` gives its text) is a `Dynamics` (`events/dynamics.h`) whose marking is that name. A `Dynamics` targets a `TimeSpan` and has no position of its own, so each marking holds from its position to the next later marking in the same part, or to the part's end ("in force until the next"); markings at one position share a span, and the `<offset>` moves a marking. One with no extent (at or after the part's end) is skipped with a warning. The staff of its `<direction>` and its part are kept in parallel arrays. Wedges (crescendo, diminuendo) are not read.
- **The vendored parser.** The XML is parsed by ezxml (MIT, Aaron Voisine; the `lxfontes/ezxml` mirror), vendored unmodified under `third_party/ezxml/` with its `license.txt` and a README that records the source and a SHA-256 of each file. It builds as the private static target `ursatz_ezxml`, linked PRIVATE to `ursatz`, and only `src/io/musicxml_importer.c` includes it; `tests/test_architecture_third_party.c` fails if anything else does, and no type of it is in a public header, so it can be replaced by changing that one file. ezxml parses in place, so the importer gives it its own copy, strips a UTF-8 byte order mark and trailing space, rejects a NUL byte, and caps the size first; input is treated as untrusted. `tests/io/test_architecture_io.c` allows the one include.
- **Round trip.** `tests/io/test_musicxml_roundtrip.c` takes each framework-v1 reference piece through MIDI import, `musicxml_export_write` and `MusicXmlImport` and compares the note multisets (sounding pitch, onset, duration). `musicxml_export_write` has no `MeterMap`, so it lays a defaulted 4/4 and writes no key; meter and key are not compared there. The export is exact (`<divisions>` is chosen per piece), so Bach 114 (430 notes), Field 5 (1083) and Mozart 545 (5598) come back EXACTLY equal, which is asserted. Clementi 36 and Field 1 are two-channel files whose notes carry no voice, so the two hands overlap in one implicit voice and `musicxml_export_write` refuses them (`MUSICXML_EXPORT_ERR_OVERLAPPING_NOTES`). The real-meter round trip, with meter, tempo, keys, parts and staves compared, is `tests/export/test_musicxml_score_reference.c` (see `docs/modules/export.md`). The importer's own exactness is proved by the hand-written fixtures in `tests/fixtures/musicxml/` (`test_musicxml_importer.c`), one per mapping rule.
- **Limits.** No `.mxl`, no `score-timewise`; repeats and endings are not unfolded (notes are imported in written order); grace notes are skipped, so no grace-note timing; articulations, slurs, lyrics, wedges, layout and engraving are not read (they belong to the Notation Document Model); microtonal alters are rounded; a measure of irregular length cannot be put in a `MeterMap`; a key and tempo are read, never inferred; `<words>` that are not beside a metronome are not tempo text. `MusicXmlExport` is unchanged and still writes a single part with a synthetic 4/4 (real meter in export is later work).

`import_notes.h` (`midi_import_analysis_notes`, `musicxml_import_analysis_notes`, `import_analysis_notes_destroy`): the neutral notes the analysis chain and the framework adapters read (`semantics/analysis_note.h`, R-242), made from an import in one call, so no caller writes the converter. One `AnalysisNote` per imported event, sorted by `analysis_note_compare` (onset, then sounding pitch, then id). The import is not modified and must outlive the notes: the event, the note id (the event's `EntityID` value), the spelling and the voice id (the target of the event's `VoiceReference`, NULL when the note names none) are borrowed. The span (the event's onset to onset plus duration, left-closed) is built here, so the array is freed with `import_analysis_notes_destroy`, not `free`. `midi` is the semitone number of the import's parallel `PitchNumericValue` (the sounding pitch); `track` is the MTrk chunk of the note for MIDI and the part index for MusicXML; `voice` is `ANALYSIS_INDEX_NONE` (nothing here assigns voices); `voice_confidence` is 1 for a voice the source gave and 0 for none. An event that makes no valid `AnalysisNote` (a zero-length span, a pitch outside 0 to 127) fails the call with `*out` untouched. io includes `semantics/analysis_note.h` for it (the architecture test allows it). `tests/io/test_import_notes.c` checks the counts, the order and every borrowed field on a corpus MIDI file and three MusicXML fixtures, and runs under valgrind.

## Notes

- `MIDIImporter` is built from three internal pieces: `smf_reader` (byte-level SMF header/track chunk parsing), `midi_event_decoder` (walks one track's decoded bytes once and extracts note-on/note-off events, program changes, the track name, time signatures and tempos, including running status), and `midi_importer` itself (matches note-on/note-off pairs, converts to `NoteEvent`, flattens and time-orders across tracks). Only `midi_importer.h` is a public entry point; `smf_reader` and `midi_event_decoder` are implementation detail.
- **Tempo-independent units.** `midi_importer_import` does not read tempo meta-events (`midi_importer_import_with_tempo` returns them as a `TempoMap`, separately), and no tempo is assumed. `MusicalTime`/`Duration` are produced as an exact whole-note fraction derived from tick counts and the header's ticks-per-quarter-note (PPQN) division field alone: a quarter note is `PPQN` ticks, a whole note is `4 * PPQN` ticks, so a tick position/duration becomes `numerator = ticks`, `denominator = 4 * PPQN` (exact rational, Law 19). No BPM/seconds conversion is performed -- the same tick count always yields the same `Duration` regardless of tempo, since PPQN is fixed per file and a tick carries no tempo information of its own until combined with a tempo meta-event (not read here). A file with an actual tempo map still has no real-world playback duration recovered by this importer; that remains a deliberate scope cut (see Deferred), it just no longer means `Duration` itself is tempo-dependent.
- SMPTE-format division (the header's division field with its top bit set) is rejected as malformed rather than decoded -- consistent with "fail cleanly on anything not a well-formed SMF 0/1 file" rather than attempting best-effort support.
- Note-on/note-off pairing is done independently per track (MIDI convention: a note-on and its matching note-off always live in the same track), matching each note-on to the earliest following unmatched note-off with the same channel and note number. An unmatched note-on at the end of a track (no corresponding note-off) is treated as a malformed file and fails cleanly, rather than being inferred as ending at track end.
- **Provenance.** This is likely the first real, populated (non-test) use of `ProvenanceReference` (`core`, L1) in this codebase. No `ProvenanceActivity`/`ProvenanceAgent` type exists yet anywhere in the codebase -- that is legitimate future work, scoped separately, not a silent addition here. Instead, `MIDIImporter` constructs one stable `EntityID`, `"midi-importer-v1"`, and every `NoteEvent` it produces points its `ProvenanceReference` at that same id.
- Pitch conversion goes through the existing `PitchNumericValue` → `PitchIdentity` path (`pitch_numeric_value_create` + `pitch_numeric_value_to_identity`), under one importer-local `TuningSystem` labeled `"MIDI note number"` -- a plain linear space where a `PitchNumericValue` position of N means "MIDI note number N," with no 12-TET or A440 assumption baked in beyond what the MIDI note number itself already is. No parallel pitch-conversion path was introduced.
- **PitchSpelling.** Every `NoteEvent` also gets a `PitchSpelling` (letter, accidental, octave), set on `optional_pitch_spelling`. A MIDI note number carries no key context, so this importer always spells the 5 black-key pitch classes as the sharp of the letter below (accidental = 1) rather than the flat of the letter above -- e.g. MIDI note 61 is always spelled C#, never Db. This is a fixed, key-signature-unaware convention, not a general enharmonic-spelling model; nothing elsewhere in the codebase spelled pitches before this. Octave follows the standard MIDI convention (`octave = note / 12 - 1`, so MIDI 60 = C4).
- **Numeric pitch output.** `midi_importer_import` also returns the `PitchNumericValue` it computed for each `NoteEvent`, via a second output array (`out_pitch_values`) index-paired with the `NoteEvent` array (same count, same order). This exists because `PitchIdentity`'s conversion is intentionally one-directional (see `pitch/pitch_numeric_value.h`) -- there is no way to recover a numeric pitch from a `NoteEvent`'s opaque `PitchIdentity` after the fact, so a caller needing numeric pitch data (e.g. for chord/key analysis) has no source for it other than this importer exposing the value it already computed. The caller owns the returned array and every `PitchNumericValue` in it (destroy each with `pitch_numeric_value_destroy`, then free the array). This does not weaken or bypass `PitchIdentity`'s opacity guarantee in any way -- it is a plain by-product of this importer's own MIDI-note-number tuning system, exposed only for the `NoteEvent`s this importer itself produced.

## Deferred

Deliberate scope cuts for `MIDIImporter`, not gaps to be filled incidentally:

- `midi_importer_import` itself does not read tempo meta-events; `midi_importer_import_with_tempo` returns them as a `TempoMap`. MIDI rendering or export, `MetronomeMarking`/`TempoMarking` from MIDI tempo, and tempo or rubato inference from note timing are not done.
- `midi_importer_import` itself does not read time signature meta-events; `midi_importer_import_with_meter` returns them as a `MeterMap`. Beats, subdivisions and beat strength are not computed, and no meter or pickup is inferred from note content.
- `midi_key_signature_scan` reports only the first Key Signature meta-event it finds; key changes are read by `midi_key_signature_scan_all`. Deciding a key or detecting a modulation from them is analysis work, not done here.
- Controller (CC), pedal, program change, pitch bend, and aftertouch events are ignored, not errored on.
- Channel-aware `Voice` assignment is not attempted for multi-channel imports -- those `NoteEvent`s are flattened into one time-ordered sequence with `optional_voice == NULL`, same as before. A single-channel import (matched notes all from one channel, regardless of how many note-bearing MTrk chunks they come from) is the one exception: it now gets a `VoiceReference` assigned per `NoteEvent` via greedy interval-graph coloring by timing, scoped independently within each source track, purely so `MusicXmlExport` (`music-export`) can represent overlapping notes (e.g. two-handed piano recorded onto one track/channel, or a two-staff piece with RH/LH on separate tracks) without a false-positive overlap error. Voice ids are namespaced by track, so two tracks that each land on local slot 0 never collide into the same exported voice. This is an export-grouping label only -- no musical/analytical meaning, no melody/harmony distinction, and it is a placeholder pending Deliverable F (Container and Structure Specification). No backfill: only new imports get this.
- Malformed/unusual header recovery is not attempted. Anything that is not a well-formed SMF type 0 or type 1 file fails cleanly with a defined error, rather than being best-effort recovered.
- SMF type 2 files are rejected as unsupported, not parsed.
- Key-signature-aware spelling (choosing sharps vs. flats per the piece's actual key) is not attempted -- this importer has no key-detection step to draw on, and always applies the fixed sharps-only convention described above.

Out of scope entirely for this module, not missing: renderers, importer formats other than SMF and MusicXML, and `DigitalArtifact`.

## Dependencies

Depends on `identity` (L0), `core` (L1), `time` and `pitch` (L2), and `events` (L3) only. `MeterMap` and `TempoMap` are in `time`; the importer does not depend on `frameworks/standard-meter` or any framework.
