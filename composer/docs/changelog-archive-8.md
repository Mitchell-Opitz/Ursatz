# Changelog archive 8

The Composer changelog entries of phases P60 and P59. Back to the [changelog](changelog.md).

## Unreleased (phase P60)

A section's harmony is given in a piece request (R-610, B7; A20261115-655). A game loop section or an overlay of a sized form takes `harmony`: `{"progression": "i iv V i", "cells": 2}`, `{"schema": "prinner"}` or `{"chords": [{"bar": 2, "text": "V"}]}` (bars from 1), given before composing by `piece_give_harmony` (`piece/section_harmony.c`): a progression with `plan_give_progression`, a schema (`harmony_schema_chords`, its stages' numerals in the section's key, a cell each; refused for a section that changes key) and chords with `plan_give_chords` through `request_read_chords`, the theme request's chord reader moved to `util/request_chords.c` (it takes the first bar, 0 for a theme and 1 for a section). `piece_check_harmony` tries it on a scratch plan so the API refuses at `/request/sections/<i>/harmony` with the reason: a theme fill ("a theme brings its harmony"), a section that returns another or an operator section, a progression past the section, a numeral or chord that cannot be read. The old progression fill is read as `harmony.progression` with an empty fill and refused beside `harmony`; `PIECE_FILL_PROGRESSION` and `PieceSection.numerals`, `numeral_count` and `cells_per_chord` go, and the reply's `fill` is `"empty"` for it (`piece-progression-fill`). The rows gain `harmony` and the vocabulary `schemas` (`fill_kinds` no longer lists `progression`). Nothing composed moves. New: `test_piece_harmony`. See [piece-request.md](piece-request.md).

A piece request gives each section its own controls (R-610, R-611, B6; A20261115-654). A game loop section is read through the section description (`PieceSection` holds `SectionDescription description`; `piece_section_init`, `piece_section_part`, `piece_section_function` and their setters; `piece_part_from_name` and `piece_function_from_name` go): `role` is the new name of `part`, `bars` another way to give `beats`, a refusal keeps its path and has the codec's message. A section asks for a key with `region` (`"home"`, `{tonic, material}` or `{relation, anchor}` from `home`, `previous` or an earlier section): `piece_resolve_regions` and `PieceRegion`, refused at `/request/sections/<i>/region` for a material the Composer does not write (P69) or an anchor that is not before the section; the plan's key lane has a Given span for each run of sections in one key, the seam takes the first body section's key, a relation span is named by it and its anchor (`PLAN_KEY_ANCHOR_SECTION`, `PlanKeyRelation.anchor_section`, the plan JSON anchor is `home`, `previous` or the section's name, `plan_lane_span_set_key_relation` takes the section), and the movement's home region is the plan's first key (`RenderedKey.tonic`). A form with sizes takes `sections` as overlays (`PieceRequest.overlays`, `overlay_count`; `piece_resolve_overlay_regions`): a section of the size by `name` with a region, a motif with a motive of its own or a composed theme; the other sections and their draws are as before, `piece_plan_keys` takes the regions and `piece_plan_cadences` runs for them. A motif section whose motive is not the piece's has a motive node `own <section>` in the material (`piece_add_own_motive`, `piece_add_own_ref`), a game loop's later motif sections included: a request that gave them motives was composed with the first's before, so a plan, its MIDI and its hash move (`piece-loop-and-ending`). The reply rows gain `region` beside `key` (null for none) and the vocabulary `relations`; `piece.request.schema.json` takes the new members and the overlays, referencing the section fragment, and the responses' schemas and `vocabulary.schema.json` the new ones. The API stays 2.2. New: `test_piece_sections` (the R-611 ternary with A in C minor and B in E flat major from a theme in each mode, `previous`, an own motive, a game loop body in the dominant, the refusals).

The plan's constraint kinds go through one table (R-609, B5; A20261109-71). `src/plan/constraint_kinds.c` has one `ConstraintKindRow` per kind in `PlanConstraintKind` order (`constraint_kind_row`, `constraint_kind_named`): the kind's name in the plan file and its `valid`, `write` and `read` functions, which are the case bodies that `constraint_is_valid` (`constraint.c`), `constraint_json` and `read_constraint` (`plan_json.c`) had; those three now look the row up and call it, and no `case PLAN_CONSTRAINT_` is left outside the table. The reading helpers the kinds use alone (`read_motive_ref`, `read_motive_tones`, the pre-relation-step transform names) moved with them; the ones the file reader shares are declared in `plan_json_internal.h` (`json_read_enum`, `json_read_enum_member`, `json_read_optional_bool`, `json_read_key_members`, `json_key_members`, `JSON_ACCOMPANIMENT_NAMES`). Plan JSON is byte-identical; no golden moved. See [plan-constraints.md](plan-constraints.md#adding-a-kind).

A plan records the form it was built from (R-608, B4; A20261115-653). `PlanFormRecord` (`name`, `version`, `hash`, `checks`, `closing`; `plan_set_form_record`, `plan_form_record`) is set by `form_build_plan`, `form_build_request_plan` and `piece_perform` (`piece_set_form_record`) and written as `composer.form` of the form node (the same format 5; `schema/plan.v5.schema.json` gains `formRecord`); a section built from a form document holds its `closed`. `form_spec_builtin_plan_name` and `form_spec_builtin_hash` (FNV-1a 64 of the embedded document) read the generated plan names and the documents. `compose_run` takes its checks from `ComposeConfig.form`, else the record, else every check; `piece_check_cadences(plan, out)` loses its form argument and reads `closing` from the record and `closed` from each section's description; `form_spec_builtin_for_plan` is deleted. A plan of a format before 5 reads with the record and `closed` flags of the built-in form its form node is named for (`piece_form_record_migrate`), and a plan of no built-in form has none. Composed notes do not change; the plan snapshots and form plan fixtures move by the record and the `closed` members. New: `test_form_spec` gains the record, its migration, the cadence check and the recorded checks. See [plan-format.md](../../library/docs/modules/plan-format.md#form-record) and [forms.md](forms.md#checks).

A plan section holds its description and the plan is format 5 (R-607, B3; A20261115-652). `SectionDescription` is stored on every section node (`plan_node_section`, `plan_node_set_section`, `plan_section_or_empty`, `plan_section_named`, `plan_node_cadence`): the section's letter, role, pairing, cadences, return, layers, pedal, construction, figure, function, hold (`leads_in`) and connective are its members and not constraints. 16 kinds leave `PlanConstraintKind` and `PlanConstraint` (`archetype`, `material`, `theme_pairing`, `return`, `layers`, `section_letter`, `piece_part`, `free_phrase`, `hold`, `seam`, `pedal`, `construction`, `connective`, `liquidation`, `figure`, `section_function`; `PlanReturn`, `PlanLayers`, `PlanPiecePart`, `PlanPedal` and `PlanConnective` go with them) and a section node refuses a `cadence` constraint (`PLAN_ERR_BAD_PAYLOAD`). `plan_json.h`: `URSATZ_COMPOSER_PLAN_FORMAT_VERSION` 5; a section node writes `composer.section`, and the reader takes the old kinds of versions 1 to 4 into it (the second `cadence` of a section is `first_cadence`). `schema/plan.v5.schema.json` replaces `plan.v4.schema.json`: a node's `section` is the `plan_section` profile of the section fragment, and the 16 kinds leave the constraint enum. The fill picks its targets as before (`section_description_weight` counts the members that were constraints). Composed notes do not change; the plan snapshots and the other goldens that embed a plan move by `format_version` and the `section` member, and `test_style`'s `MAIN_HASH` is re-recorded. New: the format 4 migration, the store and the cadence read in `test_plan_json`. See [plan-format.md](../../library/docs/modules/plan-format.md#section-descriptions) and [plan-constraints.md](plan-constraints.md).

Form documents are version 2 and their sections are the library's section description, and the API is 2.2 (R-605, R-606, B2; A20261115-74, A20261115-75). `FormSectionSpec` is gone: `FormSpecSize.sections` holds `SectionDescription` (`<plan/section.h>`), read by `section_from_json` and checked by `form_section_check`; the section vocabulary (`FormRole`, `PlanThemeBeginning`, `PlanReturnVariation`, `PlanFigure`, `PlanConstruction`, `PlanSectionFunction` and the rest) is the library's `Section*` types, renamed across the Composer (`FORM_ROLE_COUNT` is `SECTION_ROLE_FORM_COUNT`, 19). A region lists relations of the snapshot (`"major": ["omt.relation.dominant"]`) in place of degrees, and `"version": 1` is refused with `form documents are version 2`; the 22 documents in `forms/` and the fixtures are rewritten. The forms entry serves a form's sections through `section_to_json`: the beginning, ending and slots of a liquidation, retransition and coda are `null`, and `forms.schema.json` allows it. `piece_variations.response.schema.json` lists the 19 form roles. `schema/form.v2.schema.json` replaces `form.v1` and references the section fragment (`library/plan/schema/section.schema.json`); the test `test_form_schema` validates every built-in form. A section may give `"variation": "exact"` alone (the default), and a cadence may be written PAC, IAC, HC, DC or PC.

## Unreleased (phase P59)

The Composer exports every plan as a work with one movement whose lines are all assigned to one piano performer part, and the API is 2.1 (R-599, R-601, B7; A20261104-52). `RenderedPlan` gains `note_ids`, `note_sources` and `note_operations`, parallel to `events` (set from the plan note, zeros for notes of `render_notes`, freed by `rendered_plan_destroy`); the NoteEvent ids stay `composer-span-<s>-note-<i>`, so the hearing reads the render as before. New `render/movement_build.{h,c}`: `rendered_plan_work(rendered, options, knowledge, &work, &error)` makes the work `w1` (no title or composer, ensemble `omt.instrument.solo-piano`) with the movement `m1` titled for the form ("piece" when it has no name), the plan's meter map (`meter_map_copy`), the options' tempo (`build_tempo_map`, moved from `export.c`), the render's key signatures, the section markers and the loop markers, and one line for each rendered part (`melody`, `bass`, `inner-<voice>`; the roles melody, bass and accompaniment; line notes `n<plan note id>` with their spelling and, where the plan has one, the derivation `n<source>` with `copy`, `motive` or `return`), then reduces it to the piano of the snapshot (`movement_reduce_to_piano`). `rendered_plan_midi_bytes` and `rendered_plan_musicxml_text` take the `KnowledgeSnapshot *` first, build the work and call `movement_export_midi` and `movement_export_musicxml`; `choose_division` and `need_division_for` moved to `io/movement_export.c`; `PLAN_EXPORT_ERR_TOO_MANY_VOICES` now says "more than 15 lines in the performer parts; MIDI has 15 channels for them". Every entry passes the snapshot it holds (`ComposerContext.knowledge`) to `api_render_outputs` and its helpers. `--plain-midi` still means no track names and no section markers, and the program changes stay. The MIDI file has the conductor and one track `Piano` with a channel for each line and a program change on each; the MusicXML file has one part `piano` named `Piano`, two staves when a line is on the lower staff (melody on 1, bass on 2, an inner voice by the mean of its notes at middle C), and each note's `xml:id` is `piano-n<plan note id>`. `COMPOSER_API_VERSION_MINOR` is 1. Composed notes do not change: the 17 `.mid` and 13 `.musicxml` snapshots are re-recorded with the same notes (`/tmp/p59_gate.py`: `mid` and `xml` equal before and after), and the listen outputs' `mid`, `xml` and `json` hashes hold. New: `test_composer_movement` (every stored plan renders into one movement with one part `piano`, one assignment per line, the staff rule, `piano-n<id>` ids, the motive links on the line notes, one part track with five channels for a `layered` piece, and the MIDI notes per channel and the MusicXML notes equal to those of a render as voice tracks). `test_export_daw` writes the plain MIDI through the library renderer with the lines as one part. See [export.md](export.md) and [api/vocabulary-and-validation.md](api/vocabulary-and-validation.md#api-21-midi-and-musicxml-layout).

Every plan note has an id, and the plan is format 4 (R-601, B6; A20261104-25). `PlanNote` gains `id`, `source` and `operation` (`PlanNoteId`, `PLAN_NOTE_NONE`, `PlanNoteOperation`: `PLAN_NOTE_FROM_NONE`, `_COPY`, `_MOTIVE`, `_RETURN`) after `accidental`, so `plan_note()` and every positional initializer stay valid and a note the operators write has id 0. `PiecePlan` gains `next_note_id` (1 in a new plan, only rising, moved by `plan_replace_contents`); `plan_add_lane_span` and `plan_lane_span_write` give the ids on the stored copy (`plan_note_ids_assign`): a note with id 0 gets the next id, a note whose id another live span holds gets the next id with the old one as its source and operation `copy` (when it has no source), and any other note keeps its id. `plan_next_note_id` and `plan_note_by_id` read them. `return_copy_write` gains the operation: a return inside its plan (`return_apply`) gives each copied note its id in the copy as source and operation `return`, and `plan_give_section` clears all three, so a theme given to a piece is made from nothing there. `MelodyContext` gains `motive_note_id`, and `melody_apply` and `melody_candidate_realized` give each note that carries a motive note `source` = that note's id and operation `motive` (a developed motive node's own notes have no link). The code that wrote `PlanNote` members one by one into uninitialized storage now zeroes the note first (the placeholders, the bass, accompaniment, voicing and counterpoint writers). `plan_json.h`: `URSATZ_COMPOSER_PLAN_FORMAT_VERSION` 4; the writer adds `next_note_id` after `format_version` and `id` (and `source` and `operation` when there is a source) on every note; the reader takes versions 2 to 4, gives a version 1 to 3 file ids 1 to n in file order and refuses a repeated id, an id below 1, and a missing or too low `next_note_id` with the member's path. `schema/plan.v3.schema.json` is `plan.v4.schema.json` (`format_version` 4, `next_note_id`, the note members, and the lane enum's `inner-voice` is `inner_voice`, what the writer writes). Composed notes do not change; the 19 plan snapshots and the other goldens that embed a plan move by `format_version`, `next_note_id` and the note members only, and `test_style`'s `MAIN_HASH` is re-recorded. The API version waits for B7. New: `test_plan_note_ids`. See [plan-format.md](../../library/docs/modules/plan-format.md#note-ids).
