# Changelog

The Composer versions and what each changed. Back to the [docs index](README.md). Older entries are in the [changelog archive](changelog-archive.md).

## Unreleased (phase P59)

The Composer exports every plan as a work with one movement whose lines are all assigned to one piano performer part, and the API is 2.1 (R-599, R-601, B7; A20261104-52). `RenderedPlan` gains `note_ids`, `note_sources` and `note_operations`, parallel to `events` (set from the plan note, zeros for notes of `render_notes`, freed by `rendered_plan_destroy`); the NoteEvent ids stay `composer-span-<s>-note-<i>`, so the hearing reads the render as before. New `render/movement_build.{h,c}`: `rendered_plan_work(rendered, options, knowledge, &work, &error)` makes the work `w1` (no title or composer, ensemble `omt.instrument.solo-piano`) with the movement `m1` titled for the form ("piece" when it has no name), the plan's meter map (`meter_map_copy`), the options' tempo (`build_tempo_map`, moved from `export.c`), the render's key signatures, the section markers and the loop markers, and one line for each rendered part (`melody`, `bass`, `inner-<voice>`; the roles melody, bass and accompaniment; line notes `n<plan note id>` with their spelling and, where the plan has one, the derivation `n<source>` with `copy`, `motive` or `return`), then reduces it to the piano of the snapshot (`movement_reduce_to_piano`). `rendered_plan_midi_bytes` and `rendered_plan_musicxml_text` take the `KnowledgeSnapshot *` first, build the work and call `movement_export_midi` and `movement_export_musicxml`; `choose_division` and `need_division_for` moved to `io/movement_export.c`; `PLAN_EXPORT_ERR_TOO_MANY_VOICES` now says "more than 15 lines in the performer parts; MIDI has 15 channels for them". Every entry passes the snapshot it holds (`ComposerContext.knowledge`) to `api_render_outputs` and its helpers. `--plain-midi` still means no track names and no section markers, and the program changes stay. The MIDI file has the conductor and one track `Piano` with a channel for each line and a program change on each; the MusicXML file has one part `piano` named `Piano`, two staves when a line is on the lower staff (melody on 1, bass on 2, an inner voice by the mean of its notes at middle C), and each note's `xml:id` is `piano-n<plan note id>`. `COMPOSER_API_VERSION_MINOR` is 1. Composed notes do not change: the 17 `.mid` and 13 `.musicxml` snapshots are re-recorded with the same notes (`/tmp/p59_gate.py`: `mid` and `xml` equal before and after), and the listen outputs' `mid`, `xml` and `json` hashes hold. New: `test_composer_movement` (every stored plan renders into one movement with one part `piano`, one assignment per line, the staff rule, `piano-n<id>` ids, the motive links on the line notes, one part track with five channels for a `layered` piece, and the MIDI notes per channel and the MusicXML notes equal to those of a render as voice tracks). `test_export_daw` writes the plain MIDI through the library renderer with the lines as one part. See [export.md](export.md) and [api/vocabulary-and-validation.md](api/vocabulary-and-validation.md#api-21-midi-and-musicxml-layout).

Every plan note has an id, and the plan is format 4 (R-601, B6; A20261104-25). `PlanNote` gains `id`, `source` and `operation` (`PlanNoteId`, `PLAN_NOTE_NONE`, `PlanNoteOperation`: `PLAN_NOTE_FROM_NONE`, `_COPY`, `_MOTIVE`, `_RETURN`) after `accidental`, so `plan_note()` and every positional initializer stay valid and a note the operators write has id 0. `PiecePlan` gains `next_note_id` (1 in a new plan, only rising, moved by `plan_replace_contents`); `plan_add_lane_span` and `plan_lane_span_write` give the ids on the stored copy (`plan_note_ids_assign`): a note with id 0 gets the next id, a note whose id another live span holds gets the next id with the old one as its source and operation `copy` (when it has no source), and any other note keeps its id. `plan_next_note_id` and `plan_note_by_id` read them. `return_copy_write` gains the operation: a return inside its plan (`return_apply`) gives each copied note its id in the copy as source and operation `return`, and `plan_give_section` clears all three, so a theme given to a piece is made from nothing there. `MelodyContext` gains `motive_note_id`, and `melody_apply` and `melody_candidate_realized` give each note that carries a motive note `source` = that note's id and operation `motive` (a developed motive node's own notes have no link). The code that wrote `PlanNote` members one by one into uninitialized storage now zeroes the note first (the placeholders, the bass, accompaniment, voicing and counterpoint writers). `plan_json.h`: `URSATZ_COMPOSER_PLAN_FORMAT_VERSION` 4; the writer adds `next_note_id` after `format_version` and `id` (and `source` and `operation` when there is a source) on every note; the reader takes versions 2 to 4, gives a version 1 to 3 file ids 1 to n in file order and refuses a repeated id, an id below 1, and a missing or too low `next_note_id` with the member's path. `schema/plan.v3.schema.json` is `plan.v4.schema.json` (`format_version` 4, `next_note_id`, the note members, and the lane enum's `inner-voice` is `inner_voice`, what the writer writes). Composed notes do not change; the 19 plan snapshots and the other goldens that embed a plan move by `format_version`, `next_note_id` and the note members only, and `test_style`'s `MAIN_HASH` is re-recorded. The API version waits for B7. New: `test_plan_note_ids`. See [plan-format.md](plan-format.md#note-ids).

## Unreleased (phase P55)

The Composer deletes what no application reaches (R-548, B4). The Analyzer result loader (`plan_from_analyzer_result`, `analysis_load.h`), the harmony octave operator (`harmony_octave.h`) with the non-Given prolongation path (`harmony_prolong_register`) and the file layer (`plan_write_json_file`, `plan_read_json_file`, `plan_export_midi`, `plan_export_musicxml`, `motive_load_file`, `PLAN_ERR_IO`, `PLAN_EXPORT_ERR_IO`, `MOTIVE_ERR_IO`) are gone: the library reads and writes text, and the caller reads and writes the file. The check oracles (`harmony_check_lane`, `harmony_check_lane_without_cadence`, `harmony_hear_lane_cadences`, `harmony_shape_keeps`, `melody_check_lane`, `form_figure_check`) and the voice-leading hearing (`voice_hear`) moved to `tests/support`. The wrappers only tests called are deleted (`grow_build_plan`, `form_hear`, `form_hear_with_sections`, `composer_style_load`, `composer_style_measure`, `plan_regenerate`, `plan_regenerate_scope`, `piece_check_keys`, `return_hear`, `analyzer_check_piece`, `grow_fidelity_minimum`, `piece_material_bars`, `harmony_roman_parse_applied`, `variant_recognize`, `motive_connection`, `motive_connection_score`, `composer_status_name`, `hearing_analyzer_calls`, `motive_to_json`) with the functions nothing calls (`fill_relatives`, `form_check_name`, `motive_format_name`, `motive_analysis_print`, `composer_preferences_is_default`, `plan_walk`, `theme_shape_half_count`, `theme_shape_half_at`, `grow_slot_function`, `fill_suggestion_operator`, `motive_duration_name`). The 27 stray test outputs at the Composer root are removed. Composed output does not change; the API version stays 1.25.

## Unreleased (phase P53)

API 1.25 serves the sonata members (R-525, B3). The forms entry's section `mode` takes `"home"` (`FormSectionSpec.home_mode`) and the role `elaboration` reads as every role does. `form_return_mode_change(plan, section, &mode)` (`form_return.h`) is true when a section's return copies into the other mode of its source's keys, a `home` return in a minor piece or a figurate return in the parallel mode, and gives the mode of the copy. The rows' `changes` gain `mode` (`"major"`, `"minor"` or `null`) after `setting`, and `text` the part `mode: mapped into minor` before the harmony part; the row text buffer is 256 bytes. Composed output is unchanged. `schema/api/forms.schema.json` (`mode` gains `home`), `piece.response.schema.json` (the row role gains `elaboration`; `changes.mode`) and `piece_variations.response.schema.json` (`changes.mode`, required). `api_forms_response_core.json` is re-recorded (it was behind since API 1.20). New `test_api_sonata` (`slow`, 41 s: `sonatina` in A minor, B1 `changes.mode` `minor`, E in F major; in C major B1 `null`) and the sonatina cases of `test_api_forms`. See [api/theme-and-piece.md](api/theme-and-piece.md), [api/vocabulary-and-validation.md](api/vocabulary-and-validation.md) and [sonata.md](sonata.md).

The role `elaboration` and the sonatina forms (R-523, B2). `FORM_ROLE_ELABORATION` follows `FORM_ROLE_CODA` (`FORM_ROLE_COUNT` is 19; a theme-like role with no rules of its own, label `Elaboration`; `schema/form.v1.schema.json` lists it). `forms/sonatina.json` and `forms/sonatina-tonic-major.json` (92 bars, tempo 132, closing, modulating, one size, no meters), after `sonata-rondo` and before `game-loop` in `COMPOSER_FORMS`, so the forms entry lists 22: A T B C1 C2, E (B returned `embellish` in IV or VI), P S R, A1 (A returned `exact`), T1, B1 and C3 (B and C1 returned `reharmonize` in the home mode in `sonatina`, `exact` in the tonic major in `sonatina-tonic-major`), C4 and K. No other form's plan or output changes: `test_form_plans record` added only the two forms' lines (24). New: `test_sonata_forms` (slow, 5 and 2 minutes: each form composes 10 of 10 in all eight rows of key and meter with the seed tries and the keys, E, S, B1, C3 and K are checked), the sweeps of `test_form_templates` (sonatina 13 of 20 runs, tonic major 15 of 20; the given motive in C major 4/4 is stuck in both) and `test_piece_keys`, and the reading of the role in `test_form_spec`. Documented in [sonata.md](sonata.md) and [forms.md](forms.md).

A returning section may be at home in the home mode (R-524, B1). `PlanReturn` gains `across_modes`, valid only with `reharmonize` (the constraint check; the reader refuses it elsewhere with `only a reharmonized return crosses modes` at `<path>/across_modes`; the writer adds `"across_modes": true` only when set, so every existing plan JSON is byte for byte the same; `schema/plan.v2.schema.json` lists the member). `FormSectionSpec` gains `home_mode`; the reader takes `"mode": "home"` beside `"parallel"` and `"major"` (refused with `keys`, without `returns` and with any variation but `reharmonize`, each at `/mode`) and `schema/form.v1.schema.json` lists it. `form_build_plan` writes `across_modes` into the section's RETURN. `return_mode_shift_by` gives the tonic step between sources and targets in the other mode (`return_mode_shift` is it with the step 0); `return_geometry` accepts a `reharmonize` return with `across_modes` that has one, and `make_payload` moves the copy by the step, then maps it into the target's mode. Without the opt-in no `reharmonize` return crosses modes, so no built-in form changes and every output, snapshot and hash is byte-identical. New: `test_form_return home` (slow, 38 s: the 56-bar stand-in with B1 `reharmonize` in the home mode composes 10 of 10 in C major and A minor 4/4 and in G major and D minor 2/4, 10, 9, 9 and 8 on the first seed; B1's key lane is home, its RETURN has `across_modes` and its melody is B's with the pitches moved by the tonic step and, in minor, mapped), the refusals in `test_form_spec` and the round trip and refusal in `test_plan_json`. See [forms.md](forms.md), [piece.md](piece.md) and [plan-constraints.md](plan-constraints.md).

## Unreleased (phase P52)

The forms entry and the rows name the setting and the tonic major, and the API is 1.24 (R-521, B7). Each section of the forms entry gains `setting` (`null`, or the pattern of a `setting` return: `"arpeggiated"` for A2 of the small rondos and A3 of the large rondo and the sonata rondo) after `variation`, and its `mode` takes `"major"` (B1, R-517) beside `"parallel"`. Each row's `changes` gains `setting` after `variation`: `null` unless the section's RETURN is a `setting`, else the pattern the plan's RETURN carries after B4's substitution, and its text gains `accompaniment: <pattern> (new setting)` before the harmony part. Composed output is unchanged, and no snapshot holds a `changes` member, so none changed. The schemas of the forms entry, the piece response and its variations form list the members (`variation` is now an enum of the eight values). New: `tests/test_api_rondo.c` (slow, 10 s: A1 `embellish` with notes added, A2 `setting` `arpeggiated` with `new setting` in its text, B1 in C major (A major in A minor) and R1 home); `test_api_forms` reads the members and allows `"major"` only on a returning section. Documented in [rondo.md](rondo.md), [api/theme-and-piece.md](api/theme-and-piece.md) and [api/vocabulary-and-validation.md](api/vocabulary-and-validation.md).

The large rondo and sonata rondo forms (R-520, B6). `forms/large-rondo.json` and `forms/sonata-rondo.json` (88 bars, tempo 132), after `small-rondo-abaca` and before `game-loop` in `COMPOSER_FORMS`, so the forms entry lists 20. Each is closing and modulating with one size and no meters: A T B R A1 (returns A `embellish`), then C in the `trio` region (large) or P in `development` and S in `sequence` (sonata, S returns P `exact`), R1, A2 (returns A `reharmonize`), T1, B1 (returns B `exact` in the tonic major), R2, A3 (returns A `setting` `arpeggiated`) and K. No other form's plan or output changes: `test_form_plans record` added only the two forms' lines. `test_rondo_forms` (slow) composes each in eight rows of key and meter, seeds 1 to 10, 10 of 10 in every row with the seed tries (the sonata rondo in D minor 6/8 needs 46 runs, 9.5 s a seed), and checks the B1, A2 (melody kept), A3, C, P and S keys, S's melody moved from P's, R2 and the coda; `test_form_templates` and `test_piece_keys` sweep each (large 20 of 20; sonata 15 of 20 in the template sweep, whose given motive in C major 4/4 is stuck 5 times, and 20 of 20 in the key sweep). The key check no longer asks a sequence that follows its pattern for a pivot chord (S opens on P's own first chord, R-492). Documented in [rondo.md](rondo.md) and [forms.md](forms.md).

The Andante and small rondo forms (R-520, B5). `forms/andante-aba.json` (44 bars, tempo 72), `andante-abab.json` (56, 72), `small-rondo-ababa.json` (68, 88) and `small-rondo-abaca.json` (64, 88), after `main-and-subordinate` and before `game-loop` in `COMPOSER_FORMS`, so the forms entry lists 18. Each is closing and modulating with one size and no meters: A, T to the subordinate region, B (motive inverted), R, A1 (returns A `embellish`) and K, with T1 and B1 (returns B `exact` in the tonic major) in the Andante ABAB and the small rondo ABABA, R1 and A2 (returns A `setting` `arpeggiated`) in the small rondos, and C (a contrast in the `second` region, vi or IV, VI or iv in minor) in ABACA. No other form's plan or output changes: `test_form_plans record` added only the four forms' lines. `test_rondo_forms` (slow) composes each in eight rows of key and meter, seeds 1 to 10, 10 of 10 in every row with the seed tries, and checks B's key, the retransitions, A1, B1 and the section after it, A2, C and the coda's tonic; `test_form_templates` and `test_piece_keys` sweep each in C major 4/4 and A minor 3/4 (every run composes). The key check no longer asks a retransition for a pivot chord (R-505 opens home straight over V, which is a pivot from V and none from IV or vi). B1 is not closed, so in a major piece its PAC is planned as a half cadence and in a minor piece it keeps its PAC (the tests expect both). Documented in [rondo.md](rondo.md) and [forms.md](forms.md).

A new return variation `setting` (R-518, B4). `PLAN_RETURN_SETTING` follows `PLAN_RETURN_EMBELLISH`; `PlanReturn` gains `setting`, one of `block`, `arpeggiated`, `alberti` or `oom-pah` (required by a `setting` return and refused on any other, in the constraint check and when a plan is read; the writer adds `"setting"` only for a `setting` return, so every existing plan JSON is byte for byte the same; `schema/plan.v2.schema.json` lists the member). `FormSectionSpec` gains `setting`; the reader takes `"setting"` (`unknown setting`, `a setting return names its setting` at `/variation` and `only a setting return has a setting`, each at its path) and `schema/form.v1.schema.json` lists the member and the variation. `form_build_plan` writes the form's pattern into the return, except the piece's own accompaniment pattern and `alberti` in a compound meter, for which it takes the next of block, arpeggiated, alberti and oom-pah. `return_vary` for `SETTING` drops the copy's inner voice spans and opens new ones over each harmony target (`read_targets`, now shared with `reharmonize`, whose output is unchanged); `return_vary_check` gains `check_setting` and `ReturnAllow` gains `ignored` (lanes left out of the comparison on both sides). No built-in form has the member, so every output, snapshot and hash is byte-identical. New: `test_form_return setting` (slow, 41 s: the 44-bar stand-in with A1 `setting` arpeggiated composes 10 of 10 in each of the eight rows of key and meter, A1's harmony, bass and melody are A's and its inner voice 1 has notes where A's has none; with an arpeggiated request accompaniment A1 is set in alberti, and an alberti setting in 6/8 is built as oom-pah), the refusals in `test_form_spec` and the round trip and refusals in `test_plan_json`. See [piece.md](piece.md), [plan-constraints.md](plan-constraints.md), [forms.md](forms.md) and [accompaniment.md](accompaniment.md).

A returning section may be in the tonic major (R-517, B3). `FormSectionSpec` gains `tonic_major`; the reader takes `"mode": "major"` beside `"parallel"` (refused with `keys`, without `returns` and with a figurate variation, each at `/mode`) and `schema/form.v1.schema.json` lists it. `draw_keys` puts a `tonic_major` section in a minor piece in the home tonic's major key (start and end, no draw, so the draws after it are unchanged) and leaves it home in a major piece; the return operator transposes major to major, the key check takes the parallel key as related (R-499) and the section after it opens home with no pivot. No built-in form has the member, so every output, snapshot and hash is byte-identical. New: refusal and reading cases in `test_form_spec`, and `test_piece_keys tonic-major` (slow, 16 s: the 56-bar stand-in composes 10 of 10 in A minor and C major 4/4, B1 is B moved by the key difference, the section after B1 is home). See [forms.md](forms.md).

A new return variation `embellish` (R-516, B2). `PLAN_RETURN_EMBELLISH` follows `PLAN_RETURN_FIGURATE` (`embellish` in `RETURN_VARIATION_NAMES` and in the `variation` enum of `schema/form.v1.schema.json`; `plan.v2.schema.json` has no enum for it). `ornament_melody` gains `short_notes`: when its scan finds no note, `embellish` takes each melody note of exactly an eighth on a cell start, contiguous with the next and not the last of its span, and splits it into two sixteenths with the added tone from `choose_tone`. `form_return` offers and proposes it (label `embellish`, up to 4 candidates) and `return_vary_check` judges it as `ornament`. `ornament` and `varied` are unchanged, so every existing output, snapshot and hash is byte-identical. New: `test_form_return embellish` (slow, 16 s: the 44-bar stand-in composes 10 and 9 of 10 in G major and D minor 2/4, A1 keeps every note of A and adds some, the same form with `ornament` composes 0 of 10) and the round trip in `test_plan_json`. See [piece.md](piece.md), [plan-constraints.md](plan-constraints.md) and [forms.md](forms.md).

A size holds up to 16 sections (R-515, B1). `FORM_SPEC_MAX_SECTIONS` is 16 (it was 9), the API's `API_MAX_SECTIONS`, so the large and sonata rondos of B5 and B6 have room for 13 and 14 sections. Every array it sizes grows with it (`FormSpecSize.sections`, `FormSpec.repeats`, the section arrays of `piece_plan_keys`, `piece_keys`, `piece_cadences`, `piece_perform` and `form_build`), and the reader's messages print it ("must list 1 to 16 groups", "at most 16 sections"). `schema/form.v1.schema.json` takes up to 16 `sections` and `repeats`. No built-in form has more than 9 sections, so every output, plan and hash is byte-identical. New: `test_form_spec` parses a size of exactly 16 sections of 4 bars (64 bars). See [forms.md](forms.md).
